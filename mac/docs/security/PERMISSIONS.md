# macOS permission and entitlement contract

bestASR requests protected access only when the user invokes the corresponding feature. The machine-readable source is `config/permissions.json`; `script/lint_permissions.sh` checks it against the committed app Info.plist, the Xcode build settings that select that file, and the app entitlement file.

| Capability | Declaration / check | Request time | Denied behavior |
|---|---|---|---|
| Microphone | `NSMicrophoneUsageDescription`, Hardened Runtime `com.apple.security.device.audio-input`; AVFoundation authorization before device setup | First microphone recording | Keep unrelated features available; show recovery without a prompt loop |
| System audio | `NSAudioCaptureUsageDescription`; Core Audio Process Tap authorization when aggregate-device I/O first starts | First selected-App or whole-Mac recording | Publish or persist no denied audio, clean up any transient tap/aggregate device, retain earlier audio, never widen the source |
| Accessibility | No Info.plist purpose key and no entitlement; `AXIsProcessTrustedWithOptions` | First insertion/enhanced mapping action | Do not read/write another app; retain text and offer manual copy/recovery |
| Calendars (v8, ENTRY-007) | `NSCalendarsFullAccessUsageDescription`, Hardened Runtime `com.apple.security.personal-information.calendars`; `EKEventStore.requestFullAccessToEvents` | When the owner switches the calendar entry on in 设置 → 入口 | Keep the entry off, read nothing, show the System Settings path |
| Reminders (v8, ENTRY-008) | `NSRemindersFullAccessUsageDescription`, same calendars entitlement; `EKEventStore.requestFullAccessToReminders` | The first click of 把下一步加到提醒事项 (a list on this Mac first; a synced list is named in the result, V8R-18) | Write nothing, show the System Settings path |

The DMG build currently keeps App Sandbox explicitly disabled pending the Process Tap, Accessibility, import, and XPC matrix. This is not permission bypass: TCC still controls all three capabilities, purpose strings remain mandatory where macOS defines them, and the committed app entitlement plist contains only Hardened Runtime audio input. Xcode base-entitlement injection is disabled so Release signing cannot silently add `get-task-allow`. Network, Apple Events automation, and App Sandbox entitlements are forbidden by the foundation lint. The inference worker has no protected-resource or network entitlement.

macOS 27 shows the Accessibility permission as 「设备控制和数据访问」 (Device Control and Data Access) under 「隐私与安全」; 「无障碍」 is the separate VoiceOver pane. The App names it that way in every string (`docs/UI-COPY.md` §2).

The delivery probe (`-MindloomDeliveryProbe`) drives other applications with the App's Accessibility permission, so it is compiled into debug builds only (`MINDLOOM_DELIVERY_PROBE` for the debug configuration in `Packages/BestASRCore/Package.swift`, `#if DEBUG` in the App) and runs only when the bundle identifier is `com.bestasr.mindloom.check` (review 10-5c P4). The product (`app.mindloom`) and the preview do not carry it, so no local program can launch them with an argument and borrow their permission. The one-shot paste probe (`BESTASR_PASTE_PROBE`), which pasted into whatever application was in front, is removed (review 10-5d R9). In the check app the probe sends nothing unless the application under test is in front with the keyboard on the probe's own surface (the same element, still empty before a paste); the rows that keep an Electron tree off on purpose cannot look at the keyboard and are sent only while nobody clicked or typed since the keyboard was placed, so they rely on the owner not touching the keyboard or the mouse. It empties a message box by keys only when that box is the element it put the keyboard in and holds exactly its own words, and otherwise takes its words out through accessibility or leaves the box alone (review 10-5d R1). It answers only a question its own close raised, keeps a copy the owner makes during the run, and puts the clipboard and the accessibility switches back as it found them; the switches are listed in the output directory before they are turned, and `-MindloomDeliveryProbeRestore` puts back what a probe that did not finish left (review 10-5d R2, R3). Once the check app has the permission, any local program could launch it with the probe argument; the permission is therefore removed again after a run (System Settings > Privacy & Security > Device Control and Data Access, select Mindloom Check, “−”), and `v12-delivery-probe.sh` prints that step at the end (review 10-5d R9).

`ProcessTapTCCDenialProbe` is a disposable device-lab target with a distinct bundle identifier and its own narrowly scoped usage description. Apple's Process Tap permission prompt occurs when recording starts from the aggregate device, so the probe creates temporary HAL objects, attempts to start I/O, and verifies either an I/O-start rejection or that callbacks contain only digital zero with the fixed synthetic watermark absent. It then requires tap/aggregate counts to return to their pre-run values. The probe starts only the signed synthetic watermark player, persists no audio, and records only OSStatus, callback/frame counts, aggregate signal measurements, and lifecycle counts. A human must explicitly confirm choosing “Don’t Allow” before the conditional observation can become canonical evidence. The workflow never changes the production app's permission entry.

The v8 share extension 「收进织机」 (`MindloomShare.appex`, ENTRY-002) is the only sandboxed component: `com.apple.security.app-sandbox` plus one home-relative read-write temporary exception for `Library/Application Support/Mindloom/entries/share-inbox/` (`bestASR` before 2026-10-06), the library's share drop folder. It has no network, file-picker or Apple Events entitlement; it hands shares to the App only through that folder and a content-free `mindloom://share-inbox` URL. The calendars entitlement covers EventKit for both the read-only calendar entry and the click-only Reminders write; its threat-model impact is recorded in the 2026-10-01 v8 note of `THREAT_MODEL.md`.

The v8 Chrome extension 「收进织机」 (ENTRY-012) adds no entitlement, usage description or TCC prompt. The App writes one file outside its library, and only when the owner switches the entry on in 设置 → 入口: Chrome's native messaging host manifest `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/app.mindloom.json` (`com.bestasr.mindloom.json` before 2026-10-06) (the bundled helper's path and `allowed_origins` = the extension's fixed ID; 0644, atomic, never through a link, never creating Chrome's own folder). Switching the entry off removes that file and nothing else. The extension itself asks Chrome only for `activeTab`, `contextMenus`, `nativeMessaging` and `scripting` (no host permissions) and its pages may not connect anywhere (`connect-src 'none'`).

The Tencent Meeting entry (ENTRY-013, off by default) adds no entitlement, usage description or TCC prompt. It bundles `Contents/Helpers/tmeet` (TencentCloud's tencentmeeting-cli v1.0.18 built from the pinned source in `third_party/tencentmeeting-cli` with Mindloom's patches), signed with the App's identity and the hardened runtime and without entitlements; only the App starts it, one whitelisted command at a time. It is the one entry that connects off this Mac: while the entry is on, tmeet connects to `api.meeting.qq.com`, `work.medialab.qq.com` and `meeting.tencent.com` with the owner's Tencent Meeting login. The login lives in `<library>/entries/tencent-meeting/` (0700), encrypted under a key kept in Mindloom's own Keychain item (`app.mindloom.tencent-meeting`, this device only, not synchronized) and handed to tmeet on an inherited descriptor; tmeet does not use the system Keychain. Before every run that hands over the key, the App checks that `Contents/Helpers/tmeet` is the code sealed into the App that is running (the App on disk is the one running, its seal holds over nested code, and the helper's code hash matches); otherwise tmeet is not started and the key is not read. Switching the entry off removes that folder (and the folder a reconnection makes its new login in) and the Keychain item on this Mac; nothing is sent to Tencent, and the authorization given on the phone stays valid at Tencent until it ends. Its threat-model impact is recorded in the 2026-10-06 note of `THREAT_MODEL.md`.

The v8 lab infrastructure (INFRA-001–007, SPACE-013–016) adds no entitlement, usage description or TCC prompt. A team member's Mac runs `/usr/bin/ssh` (as the organizing link already does) to the team's organizing device with its own key, a private known_hosts file and `-F /dev/null`; the key file exists only while ssh reads it (0600 in `<library>/team-gate`). Backups go to a folder the owner picks in an open panel (on the Mac or an external disk); a handover pack is exported through a save panel; a member plays a meeting part's audio with AVAudioPlayer (output only, no microphone). The member key, credential and space keys stay in the login Keychain (this device only).

The Apple Watch app (WATCH-001–008, `<iPhone bundle id>.watchkitapp`) asks for one permission: the watch's microphone (`NSMicrophoneUsageDescription`, `AVAudioApplication.requestRecordPermission` on the first 「录音」, never at launch). Denied: nothing is recorded, the screen names the watch's 「设置」>「隐私与安全」>「麦克风」 path, and no prompt loop. It declares `UIBackgroundModes` audio only so a recording started in the foreground goes on with the wrist down; it cannot start one in the background. It has no entitlement file, no App Group, no network code and no recognizer; recordings reach the iPhone only through WatchConnectivity. Its complication extension (`.watchkitapp.widgets`) has no permission at all. The iPhone side adds no permission: it transcribes with the recognizers the speak bar already uses and never asks for speech permission from a background launch.

Any future entitlement must name its feature, threat-model impact, runtime and distribution behavior, rollback path, and real-machine evidence before this contract changes.

New identity (2026-10-06, the owner's decision; supersedes the next paragraph's first sentence): the product is `app.mindloom` (`com.mindloom.app` was taken), installed as `~/Applications/Mindloom.app` with the executable `Mindloom`, signed with the same Apple Development certificate and team as before; its designated requirement is `identifier "app.mindloom" and anchor apple generic and certificate leaf[subject.CN] = "<the same Apple Development certificate>" and certificate 1[field.1.2.840.113635.100.6.2.1] /* exists */`. To macOS it is a new App, so the TCC grants do not carry over and are asked again by the system's own prompts: microphone (dictation and recording); 设备控制和数据访问 / Accessibility (the fn key through an active event tap, which needs Accessibility and not Input Monitoring, and typing into other Apps); 录屏与系统录音 (only when a recording of another App or the whole Mac starts); calendars and reminders (only when the calendar entry is switched on or the first reminder is added). Welcome says so after the switch (`WelcomeCopy.permissionsTextAfterBestASR`). bestASR's entries stay in System Settings (microphone, Accessibility, and Input Monitoring or Screen & System Audio Recording where earlier builds were granted them); the owner may remove them. The entitlements are unchanged (audio input, calendars). The login-keychain items do not carry over by their access lists either: a one-shot helper (`mindloom-carry-over`, built by `script/build_carry_over_helper.sh`, a separate bundle that is never part of the product) is signed with the identifier `com.bestasr.app` and the same certificate, so it satisfies the items' stored designated requirement and reads them without a dialog (any read that would need one fails instead); it hands them to Mindloom over a 0600 Unix socket in a 0700 folder of the user's temporary directory after both sides checked the peer's code signature from the kernel's audit token (`identifier` + `anchor apple generic` + the same team OU), in memory only, never through arguments, the environment, files or logs. Mindloom re-creates them under `app.mindloom.*` services; the originals are left untouched. The helper hands over only to `app.mindloom` (a check-identity helper only to another check identity) and, with `--login-item`, removes bestASR's `SMAppService.mainApp` login item once Mindloom has registered its own. Mindloom imports bestASR's preferences with `CFPreferencesCopyAppValue` from `com.bestasr.app` (read only; the App is not sandboxed), never the organizing-link (DGX Spark) keys and never bestASR's own permission history. The share extension's sandbox exception is now `Library/Application Support/Mindloom/entries/share-inbox/`, and Chrome's native messaging host is `app.mindloom`. Review fixes the same evening: a helper signed with a check identity reads only the keychain file it is given (`--keychain` is required); the offer names the library folder it was read for, and Mindloom takes it only when that is bestASR's folder beside the library it opened; the same binary signed as `app.mindloom` is the rollback's login-item helper (`--unregister-login-item`: `SMAppService.mainApp.unregister()` and nothing else); only the team-signed product opening the owner's library imports bestASR's preferences, and Mindloom never moves the library folder itself (only the switch script does). Without 设备控制和数据访问 the fn event tap does not exist and fn does nothing: the main window and the menu bar say so with 允许… until it is granted. The switch stores the external image's passphrase with `-T ""`, so every read asks.

Switch to one App (2026-10-06, before the new identity): the product is installed as `~/Applications/Mindloom.app` with the bundle identifier, entitlements and Apple Development certificate of the bestASR.app it replaces, so its designated requirement is unchanged (`identifier "com.bestasr.app" and anchor apple generic and certificate leaf[subject.CN] = "<the same Apple Development certificate>" and certificate 1[field.1.2.840.113635.100.6.2.1] /* exists */`) and the TCC grants (microphone, 设备控制和数据访问, input monitoring) and the login keychain items' access carry over; the only entitlement added since d54 is the calendars entitlement already listed above. The team ID is passed at build time (`script/signing_team.sh`), never committed. The Claude Code plugin's and Claude Desktop extension's launchers run a helper only from a copy whose bundle identifier is the product's, whose App and helper pass `codesign --verify --strict` and `anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.1] exists`, and whose App and helper carry the same team (`MINDLOOM_TEAM`, when set, pins it); an explicit `MINDLOOM_MCP` path is run as given. `script/install_local_app.sh` quits only copies launched from the applications folder, by bundle identifier, and never kills. The App re-registers its own `SMAppService.mainApp` login item from its new location once (`LoginItemRepair`); it registers nothing else.

Keychain access group (web lookup search keys, 2026-10-06 integration). The App's default entitlements stay the two above. `App/BestASR-KeychainGroup.entitlements` adds only `keychain-access-groups` = `$(AppIdentifierPrefix)$(PRODUCT_BUNDLE_IDENTIFIER)` and is used only by a build with a Mac provisioning profile for `app.mindloom` (`script/build_release.sh`, `MINDLOOM_PROFILE_SPECIFIER`): macOS refuses to start an App that carries this entitlement without such a profile (measured with a test binary signed ad hoc: exit 137). The variant reaches only the App target, through `MINDLOOM_ENTITLEMENTS_VARIANT` and `MINDLOOM_APP_PROFILE_SPECIFIER` in `project.yml` (never as a command-line `CODE_SIGN_ENTITLEMENTS` or `PROVISIONING_PROFILE_SPECIFIER`, which would override the sandboxed share extension, the worker and the MCP helper too); `script/lint_permissions.sh` holds it to the base entitlements plus exactly that one key. Without it the search keys of 「从网络补充信息」 stay in the login keychain on this Mac (`app.mindloom.lookup`), not synchronized, and Settings says so.
