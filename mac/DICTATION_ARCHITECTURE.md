# 口述架构与预算（2026-09-20）

这份文档回答两个问题：**从第一性原理出发，口述应该是什么结构**；**当前技术链在准确率、速度、资源三个方向上离最优还差多少**。所有数字都是本机实测，不是估计。

## 1. 第一性原理：口述只有一条关键路径

用户按下、说话、松开，期望文字出现在光标处。**关键路径只包含三件事**：

1. 把声音变成样本（麦克风必须已经热着）
2. 把样本变成文字（说话期间就该算完，松手时只剩尾巴）
3. 把文字放进目标 App

其他一切——词级时间戳、历史库、事件整理、说话人、统计——都是**这条路径之外的产物**，它们的正确归属是后台，且失败不应影响已插入的文字。

判断一个实现是否合理，只看一条：**关键路径上是否只剩这三件事**。

## 2. 当前预算（实测，松手到插入 P50 545 ms / P90 635 ms）

全天 24 次真实口述（插入修复之后，排除冷启动那次 5.7 s）：最快 252 ms、P50 545 ms、P90 635 ms、最慢 1403 ms。当晚最新构建的五次分别是 787（当天首次，重新加载模型 1.78 s 与之重叠）、570、591、575、**332** ms。

**长句比短句快**：9.3 s 与 7.0 s 的两段因为中间有停顿，预解码分别等 162 ms 和 0 ms 就命中（`final-asr ms=179` / `ms=14`）；1.4–2.4 s 的短句没有停顿，松手后才从头解码，`final-asr` 325–342 ms。短句解码就是现在 P50 的主要成分。

短口述（2.4–3.2 秒音频，即用户最常用的快速一句）的逐阶段实测：

| 阶段 | 实测 | 下限 | 差距来源 |
|---|---|---|---|
| 封存音频 | 50 ms | 10 ms | 可与识别重叠 |
| 解码 | 269–332 ms | ~150 ms | **说话期间只在停顿时预解码；没有停顿的短句在松手时才从头解码** |
| 词级对齐 | 74–90 ms | 0 ms | 插入不需要时间戳，它只服务历史回放 |
| 整理模型 | 0 ms（命中）/ ≤250 ms | 0 ms | 停顿时已算好则为 0 |
| 插入 | 26–28 ms（已修，原 346–378 ms） | ~25 ms | 见 3.3 |
| 其余开销 | ~80 ms | ~50 ms | 状态机每次转移都落库 |

说话期间的投机解码（停顿时预解码）已经生效：松手时通常整段命中，`qwen-speculative-hit ms=0`。

**目标预算：松手到插入 P50 ≤ 350 ms、P95 ≤ 600 ms。**

### 已经修掉的两处结构性错误（2026-09-20）

- 识别、整理、插入曾整体持有生命周期锁，导致松手后约 600 ms 内按键被当成"再结束一次"而丢弃；现在锁只覆盖封存音频。
- 每段口述结束后的历史读取（最多 10,000 行搜索 + 两个全表聚合）曾串在顺序队列里，实测每次 5.0–5.6 s，连说 4 段时第 4 段要 13.2 s 才落地；现在它在关键路径之外，且只在有人看得见时才读。连说 4 段实测已稳定在 0.9 s 左右。

## 3. 关键路径上仍然不该有的东西

### 3.1 短句在松手后才开始解码（已改）

解码内部实测（10 条 1.1–2.9 秒短句）：特征 5 ms，**编码与预填充 136–154 ms（几乎不随音频长度变化）**，逐词生成 93–146 ms，对齐 56–83 ms。

因为预填充是固定开销，"把长音频拆小"并不会更快；真正的解法是让解码**在用户松手之前就开始**。原先停顿判定要求静音 350 ms，而人说完短句往往几百毫秒内就松手，根本来不及触发，于是整段解码都落在松手之后。

已改：停顿判定改为 200 ms 语音 + **150 ms 静音**。松手时若预解码仍在进行，`take(matching:)` 会等它完成而不是重新解码；缓存的复用规则（前缀相同且其后只有静音）保证不会用错结果。代价是句间停顿也会触发预解码，靠"同一时刻只跑一个"限流。

附带收益：预解码同时算好词级对齐，所以 3.2 的对齐开销在命中时一并消失，不需要另造"事后回填历史"的机制。

### 3.2 词级强制对齐（74–90 ms）

`QwenASRRuntime` 在返回文字前运行 Qwen3-ForcedAligner，得到每个词的时间戳，用于历史回放时高亮。**插入的文字不需要它**。

应做：对齐移出关键路径，插入后在后台补算并写入历史。代价是刚结束的那条记录在几百毫秒内没有词级高亮。附带收益：对齐器 1.3 GB 权重可改为按需加载。

### 3.3 插入前那次注定失败的辅助功能直写（约 310 ms，已修）

插入先尝试用辅助功能直接写入选区：`AXUIElementSetAttributeValue` 返回"成功"，但富文本输入框（聊天软件、浏览器、Electron 编辑器）接受写入却不反映。代码为了不盲信这个"成功"，会**轮询最多 300 毫秒**确认内容真的变了，等满后才退回剪贴板粘贴——而粘贴本身只要 23–24 毫秒。

已改：确认窗口降到 40 毫秒（真正支持直写的编辑器第一次轮询就反映），并记住哪些「App + 控件角色」的直写无效，同一目标下次直接走粘贴。记忆只存在于本次运行，App 更新后会重新尝试一次。

实测：插入 345–365 ms → **26–28 ms**；松手到插入 ~820 ms → **499–528 ms**。

定位过程中的两个教训，一并记下：
- 分步计时必须用 `notice` 级别，`debug` 不落盘，事后读不到。
- 改完必须先确认改动真的写进了文件再构建：有一次脚本中途断言失败导致整文件未写回，却照常编译通过，白测了一轮。

## 4. 资源：内存里挂着口述不需要的模型

当前物理内存 5.9 GB（GPU 5.1 GB）。

| 模型 | 大小 | 口述是否需要 |
|---|---|---|
| Qwen3-ASR 1.7B 8-bit | ~2.1 GB | **需要** |
| 个人整理模型 1.7B 4-bit | ~1.0 GB | **需要**（停顿时运行） |
| SenseVoice int8（实时字幕） | ~0.3 GB | **需要** |
| Qwen3-ForcedAligner 0.6B 8-bit | ~1.3 GB | 仅为历史词级时间戳 |
| Paraformer-large + Parakeet | ~0.8 GB | 备用语种，已被 Qwen 取代 |
| 说话人模型 | ~21 MB | 冻结功能 |

已改（2026-09-20）：对齐器不再随识别器一起加载，它和整理模型都在用户开口时后台预热；最后一次口述十分钟后释放全部模型并归还 MLX 缓存。实测：**口述中/常驻 5.17 GB（MLX 2354 MB，峰值 8.18 GB），空闲 0.93 GB（MLX 归零）**。

代价：空闲释放之后的第一次口述要重新加载识别器，实测 1.8–2.5 秒，由开口时的后台预热掩盖——说得够长就感觉不到，说一句两个字的短话可能要多等一会儿。十分钟这个阈值就是按这个代价定的。

CPU：空闲期间 0%（进程运行 9 小时 57 分钟，累计 CPU 时间 32.6 秒）。磁盘：模型 5.4 GB（识别 2.3 + 对齐 1.2 + 通用 0.9 + 备用语种 0.8 + 说话人 21 MB），个人整理模型 615 MB，录音 104 MB（压缩前 578 MB，见下）。

### 录音按识别链路的格式存（2026-09-20）

采集存的是麦克风给什么就是什么——44.1 kHz float32，**173 KB/秒**。但没有任何一处按这个格式读它：识别在看到第一个采样之前就用 `BoundedPCMConverter` 转成 16 kHz 单声道，回放是人声。55 分钟的话占了 578 MB，按用户的使用强度一年约 24 GB。

现在封存后的口述会被同一个转换重写成 **16 kHz 单声道 16 位**（正是识别器评测集本身的格式），时间上连续的分块合成一个文件，所以停顿仍然是停顿、时长不变。索引、提交日志、采集元数据、以及"哪段音频产生了这段文字"的溯源一起指向新文件。

**在用户自己的录音上验证过才保留**：867,200 帧里，压缩结果与转换器本来就会产生的采样最大差 **0.0000153**，正好是 16 位量化的半步——除了量化没有别的变化；全库时长变化 23 微秒 / 54.8 分钟；238 条索引与 226 条溯源引用全部文件存在且摘要一致，没有孤儿文件。实测 **578 MB → 104 MB**。

新录音在"释放模型"的那个空闲时刻顺带压缩，那时没有任何东西还在读它。压缩必须由日志自己执行：它把每个会话的 manifest 缓存在内存里，在它背后改文件会让运行中的 App 继续按旧清单找文件，录音点不开（2026-09-20 真实发生过一次，数据没坏，重启即恢复）。

**只压口述，不压其他模式**：16 kHz 单声道是一个人对着自己麦克风说话的全部带宽，也是每个语音模型读取的格式。线下录音和电脑内录可能含音乐、房间、多人同时说话——那是以后的事件与人物功能要分析的素材，窄化不可逆。发现时已经误压了两段 48 kHz 的电脑内录（147.8 秒 / 18.3 秒），已用备份还原，`SourceAudioCompactionCLI --restore-from` 就是为此加的。

**为什么到此为止，不再上编码器（2026-09-21）**：先把曲线测完了——用户自己的 211 段从未编码过的录音（51.6 分钟），参考是 App 当时识别出的原文，"逐字差异"隔离编码器影响：

| 存储格式 | 码率 | 体积 | 字错率 | 与未编码的逐字差异 |
|---|---|---|---|---|
| 16 kHz 16 位 PCM（现在） | 256 kbps | 94.6 MB | 1.48% | — |
| AAC-LC 32 / VBR / 24 / 16 kbps | 34.9 / 28.7 / 26.8 / 18.6 | 12.9 / 10.6 / 9.9 / 6.9 MB | 1.56 / 1.42 / 1.50 / 1.68% | 0.46 / 0.50 / 0.57 / 0.87% |
| Opus 24 kbps（系统编码器） | 24.4 | 9.0 MB | 1.43% | 0.44% |
| Opus 16 kbps（系统编码器） | 16.9 | 6.2 MB | 1.45% | 0.49% |
| Opus 12 kbps | 11.3 | 4.2 MB | 1.50% | 0.78% |

结论本身是清楚的：Opus 在每个体积上都优于 AAC，系统编码器与 libopus 等价（macOS 原生支持 Opus 编解码，无需第三方库），拐点在 16 kbps。**但没有采纳**：

存下来的这份 16 kHz 16 位 PCM **就是每个模型读到的那份音频**（与转换器输出差半个量化步）。上编码器换来的是 15 倍体积，代价是**所有未来模型都只能读到有损版本**。识别上这个代价已测得是 0.49% 逐字差异；但说话人识别、事件识别对编码伪影比识别敏感得多，而"把人物和事件串起来"正是这个产品要长成的样子——那等于用一次性的磁盘收益，换掉整个未来功能栈的输入质量。按真实强度 13.5 分钟/天，现在是 9.0 GB/年，上 Opus 是 0.6 GB/年；这点磁盘买"母版始终是模型级"，值。

回放若将来确实需要小体积，正确做法是**从母版派生一份压缩副本**，而不是替换母版。要重新打开这个决定，该测的是说话人向量在编码前后的相似度，而不是字错率。

**迁入的录音按原样保存（2026-09-21）**：从旧口述工具迁入的 5,042 段历史录音本身已是压缩格式——解码成 PCM 不增加信息却涨数倍，重新编码则是第二次有损。所以逐字节复制到 `sessions/<id>/source/`，登记为该会话的 retained original（与"导入文件"用的是同一张表和同一套路径），共 151 MB，全部校验通过。macOS 原生能解该格式，以后任何模型都能按需解码读到它。

**代价**：这些录音没有进音频索引（索引假设裸 PCM 分块），所以迁入的会话在历史里没有时长、不能回放、现有的识别与说话人任务也跑不到它们。要让它们可用，需要一条"压缩源文件 → 按需解码"的读取路径——只读，不需要编码器。

### 空闲释放曾经只对"从未口述过"的 App 生效（2026-09-20 实测发现并修复）

释放前的判断要求投机解码槽为空，但那个槽只在**下一次**口述开始时才被替换，口述结束时没人归还它。于是第一次口述之后，每一次口述都照常安排释放，而释放每次都在判断处直接返回：日志里最后一条 `idle models released` 停在 10:27（一次启动预热之后），19:41、19:42、20:13 的三次口述各自安排的释放到点都没有发生，内存在 20:23:30 的截止时刻仍是 5168 MB。

修复：口述结束时归还自己的槽（顺带释放它持有的这段音频），并且判断不通过时重新安排而不是丢弃。**教训**：这类"功能其实没在跑"的失效不会有任何症状，只能靠事后核对真实日志与真实内存发现——报告一个数字之前，要确认它是在真实使用路径上测到的，而不是在某条更干净的路径上。

## 4.5 人物：阈值从未按这个模型校准过（2026-09-21）

说话人流程一直在跑（192 个任务成功、508 条出现记录），问题在匹配阈值：`SpeakerRoutingPolicy.contractProbe()`——探针用的占位值——被直接用在了线上，自动匹配门槛 0.93。

用这台机器上已存的 200 条会话向量实测：**同一个人**（跨七个月、多个房间、两个麦克风）自相似度 0.79–0.83，**两个不同的人**之间 0.11–0.17。0.93 这个模型根本达不到，于是 508 条里只有 16 条自动匹配、414 条变成"候选"等用户确认，而用户从未确认过，结果是一个人被拆成几十个匿名陌生人。

按 App 自己的增量匹配规则模拟不同阈值：

| 阈值 | 人数 | 最大簇 | 那个不同的声音 |
|---|---|---|---|
| 0.93（原值） | 176 | 17 | **被并进最大簇** |
| 0.80 | 50 | 73 | 独立 |
| **0.70** | **15** | **82** | **独立** |
| 0.65 | 10 | 120 | 独立 |
| 0.60 | 6 | 158 | 被并进最大簇 |

0.93 不只是太严——它把每个簇都打成碎片，反而让不同的声音混了进去。取 **0.70**：距离两个声音开始合并的 0.60 有 0.10 的余量，而且"把一个人拆成两个"比"把别人的话算到你头上"更容易被发现、代价更小。候选门槛同时从 0.75 降到 0.55。

历史数据用 `SpeakerRelinkCLI` 按同一规则重连（走 store 自己的 `mergePersons`，被合并的人物记录保留并标记并入谁）：**58 人 → 24 人**，最大的一个人从 45 次口述变成 **125 次**；重连后第一人与第二人的平均相似度 0.211，确实是两个人。

## 5. 技术链是否最优

### 5.1 识别模型：保留 Qwen3-ASR 1.7B 8-bit

同一评测集（240 条，其中 48 条用户逐字校对）实测，全部用同一个私有评分脚本（不公开）同一口径重算：

| | 字错率 | 5 秒以下 | 英文词召回（校对） | 与最终文字距离 | 解码中位 |
|---|---|---|---|---|---|
| **Qwen3-ASR 1.7B 8-bit + 41 词表（现用）** | **3.74%** | 8.17% | **30/41** | **34.68** | 939 ms |
| 同模型 bf16（H100，不量化） | 3.78% | 8.17% | 29/41 | 34.72 | 710 ms |
| 同模型，修特征之前 | 4.49% | 16.83% | 22/41 | 36.16 | 946 ms |
| Fun-ASR-Nano-2512 | 4.69% | 6.25% | 27/41 | 36.65 | 396 ms |
| Fun-ASR-Nano + 热词 | 7.09% | 16.83% | 30/41 | 38.53 | 2350 ms |
| SenseVoice small | 5.75% | 8.65% | 24/41 | 36.56 | 150 ms |
| FireRedASR2-AED（75 条子集，19 条校对） | 4.07% | 5.77% | 6/10 | – | 1367 ms |

**8-bit 量化不花钱**：同一模型 bf16 在 H100 上 3.78%，本机 8-bit 3.74%，差异在噪声内。继续压到 4-bit 才需要重新验证。

中英混说是硬需求，英文召回决定选型；FireRed 只在纯中文上更好且没有 MLX 移植。换更大的 Qwen3-ASR 会直接牺牲速度与内存。**结论：模型不换，提升靠微调。**

剩余的准确率杠杆，按投入产出排序：

1. ~~用用户自己的历史口述微调 ASR~~ **（2026-09-20 实测否决）**。在 2,643 条近似逐字的历史上做 LoRA（只训文本解码器，冻结音频编码器），用同一套转写脚本评测：整体字错率 **2.57% → 8.43%**，5 秒以下 4.42% → 3.87%。短句略好，长句大段漏字——因为监督信号是 Typeless 的最终文字，即使筛掉改写较多的样本，它仍然带着"删语气词、删重复"的痕迹，模型把删内容也学了。**没有大规模逐字稿，个人 ASR 微调有害**，除非先拿到逐字标注。适配器与合并权重已删除。
2. ~~上下文偏置自动化~~ **（2026-09-20 实测否决）**：从历史按词频自动选 64 个词，比用户手动整理的 41 条**更差**；只收专名的版本更差。48 条校对真值上的字错率：手动 3.74%、自动（词频）4.06%、自动（仅专名）4.65%；英文词召回 30/41、25/41、26/41。原因是自动选出的 Model、World、Cloud 这类通用词占掉名额并诱导模型输出它们。词表的价值本身是确凿的（有词表 vs 无词表：英文召回 63% → 69%，5 秒以下字错率 11.6% → 6.6%），但**选词必须由用户确认**，自动挑选这条路已关闭。相关代码与测试已删除。
3. **从用户即时修改中学习**（已在只测量阶段，见 `DictationCorrectionProbe`）。

### 5.2 整理模型：已换成 Qwen3-0.6B 8-bit

同一套数据分别训 0.6B 与 1.7B，并**在各自实际部署的量化位宽下**对比（这一点很关键：bf16 下 0.6B 更好，4-bit 下反而更差，小模型对量化更敏感）。最终用 App 自己的识别输出在 240 条上评测：

| | 与最终文字的距离 | 对校对稿精确率 | 生成中位 | 体积 |
|---|---|---|---|---|
| 1.7B 4-bit | 32.28 | 98.01% | 241 ms | 948 MB |
| 0.6B 4-bit | 32.75 | 97.94% | 166 ms | 346 MB |
| **0.6B 8-bit** | **31.77** | **98.12%** | **193 ms** | **630 MB** |

0.6B 8-bit 在每个维度都不差于 1.7B，已替换。

## 6. 防止回到"修一个补一个"

- **延迟预算写进检查**：`end-to-inserted`、`final-asr`、`insertion` 三项在固定音频上的回归测试，超出预算即失败。
- **关键路径准入规则**：任何新功能默认进后台；要进关键路径必须给出预算内的实测数字。
- **口述期间的日志只记阶段与毫秒**，不记内容，保证可诊断且不泄露。

## 8. 交互：口述瞄准的是结束的地方（2026-09-21）

这一节记录的是"可用性"那一类问题，和延迟预算同等重要：一条 545 ms 内送达的口述，如果送错了地方，等于没送到。

### 8.1 插入跟随光标，不跟随起点

插入原来要求"结束时在前台的 App，必须是按下键时在前台的那个"。这让两种最普通的用法必然失败：

- 焦点在别处（或什么都没聚焦）就开始说，说着说着点进要写的输入框；
- 起点在 A 应用，结束在 B 应用。

本机 342 次插入里失败 13 次，其中 **11 次是这一类**：

| 失败原因 | 次数 |
|---|---|
| `noCapturedTarget`（起点什么都没抓到） | 7 |
| `targetApplicationChanged` | 3 |
| `targetElementChanged` | 1 |
| `noFocusedTarget` | 1 |
| `clipboardFallbackFailed` | 1 |

现在的规则：**结束那一刻光标在哪个可编辑位置，就写到哪里**。起点只是提示（`DictationInsertionRequest.target` 变为可选）。只有三件事仍然改为复制：受保护/只读的输入框、bestASR 自己的窗口、以及**在起点那个输入框里、口述期间新选中的文字**——那段文字是用户在看，不是在瞄准。换到别的输入框时的已选文字（搜索框点进去自动全选、双击选中一个词）会被替换，和任何一次 ⌘V 一样。

### 8.2 松手不结束的三条路径

按住说、松手写，有三种情况松手信号会丢：

1. Fn 没有独立的 key-up，只有 `flagsChanged`。释放时按"当前修饰键组合"反查绑定，和按下时的匹配规则不对称，组合对不上就把释放丢了。改为和普通按键一样，释放当前挂着的那一次按压。
2. 按住期间另一路录音（线下/内录/导入）开始，`hasNonDictationWork` 把释放事件一起吞掉。改为只有按下会被这个条件拒绝。
3. 按下时如果运行时还忙，按压时间根本没记，于是释放被直接丢弃——而那次按下仍然把口述排进了队列。改为每次按下都记时间。

另外加了一道兜底：按住超过阈值后直接读硬件修饰键状态，松开就结束。事件链上任何一环丢了都不会再留下一个停不下来的录音。

### 8.3 删掉的暂停

暂停有三个入口，其中一个是**口述期间的裸空格**——它被全局拦截且不下发给前台应用。在输入框里口述完顺手打个空格，得到的是"已暂停"而不是空格。

这个功能被整体删除（自动暂停保留：睡眠、锁屏、麦克风消失时系统仍会暂停，菜单栏只在那种情况下显示"继续"）。理由：一次口述只有几秒到几十秒，没有人会去暂停它；它和打字冲突；它占着 Fn+Space，而那个组合有更值得的用途。

浮窗里的取消/暂停/完成三个按钮同时删除——口述期间指针不在屏幕角落，键盘已经能做这三件事（快捷键结束、Esc 取消）。只留"复制"，因为那是键盘做不到的一件事。

### 8.4 主窗口在口述时不再显示口述

快捷键起的口述，主窗口什么都不显示：光标在别的 App 里，浮窗已经在报状态，主窗口放一个带"暂停""结束并输入"按钮的面板，是在要求用户把指针瞄向一个他并不在的窗口。从主窗口"试一句"起的口述仍然在主窗口里看；已经停止录音、正在处理的口述也仍然显示，那是状态不是控件。

### 8.5 历史记录一次只装一页

历史页原来一次取回全部匹配记录（上限 10 000 条，本机已有 5 401 条），每条都带文字。现在每页 60 条，滚到底再取下一页；**日期与来源 App 两个筛选下推到 SQL**——留在内存里筛就没法分页，页边界会落在未筛选的顺序上。人物/事件/时长/有整理这四个筛选仍然整批取，它们都来自点击某个人或某个事件，集合本身就小。

筛选条件改为一行可单独删除的标签：筛选菜单自己是藏状态的，选完之后页面安静地少了记录，屏幕上没有任何东西说明为什么。

## 9. 翻译与指令：跑在本机 1.7B 上（2026-09-21）

Typeless 把三件事放在同一个键上：Fn 口述、Fn+⇧ 写成译文、Fn+空格 把说的话当成指令
（选中了文字就原地改写，没选中就给答案）。这两个模式现在也在。

### 9.1 为什么是和弦，不是第二个快捷键

口述键是 Fn 单键时，它在 **按下沿** 就触发；任何"Fn+其他键"的注册快捷键都抢不过它
（`GlobalHotkeyConfigurationController.overlap` 本来就拒绝这种注册）。所以复用已有的
和弦通道：原来 Fn+其他键只用来取消"Fn 误触起的口述"，现在它带上被按的那个键码，
空格 → 指令，Shift → 翻译，其余仍然取消。和弦可以在口述开始时按，也可以在说完后按，
两者含义相同——后者是"说完才决定"。

### 9.2 为什么不能走整理（polish）那条路

整理阶段的 `DictationProtectedFactValidator` 只接受 **是原文子序列** 的候选（只能删，
不能加）。这正是它对口述安全的原因，也正是它无法表达翻译的原因——翻译按定义替换
每一个词。所以这两个模式直接调本机模型，带自己的边界，替换发生在"整理完成"和
"插入送达"之间。模型答不出来时保留文本去剪贴板，而不是把没翻译的原句送出去。

### 9.3 实测（qwen3-1.7b-mlx-4bit，本机权重，`SpokenModeProbeCLI`）

模型加载 701 ms（一次），之后：

| 用例 | 耗时 | 结果 |
|---|---|---|
| 翻译·短句 | 180 ms | ✅ |
| 翻译·中英混合（pull request / CI） | 179 ms | ✅ |
| 翻译·长句 | 316 ms | ✅ |
| 指令·改写英文段落 | 173 ms | ✅ |
| 指令·改写中文语气 | 160 ms | ✅ |
| 指令·翻译选中文字 | 164 ms | ✅ 语序略生硬 |
| 指令·写一句回复 | 149 ms | ✅ |
| 指令·问事实（澳大利亚首都） | 138 ms | ✅ 堪培拉 |
| 指令·问单位换算（1 英里=?公里） | 162 ms | ❌ 答 0.62137，方向反了 |
| 指令·问算术（17×23） | 119 ms | ❌ 答 455，正确是 391 |

**结论：改写、翻译、代写这类"变换"任务在这个模型上又快又稳；算术和单位换算不可靠。**
提示词已经要求"不确定就直说，不要猜数字"，但 1.7B 在这类题上会自信地答错。答案面板
把问题和答案一起显示，就是为了让人在用之前先看一眼。

关键路径影响：模式口述比普通口述多 120–320 ms（在 P50 545 ms 的基础上），因为替换
发生在插入之前。普通口述完全不受影响——没有和弦就没有这一步。

### 9.4 一个只有实测才能发现的问题

单元测试用假生成器全部通过，真权重第一次跑却 6 条失败 5 条：模型即使被要求
non-thinking 也会吐 `<think>`，而且有两种形状——短句时**开了标签、在里面直接作答、
从不闭合**；长句时正常推理并闭合。任务管线对这两种都 fail-closed（它的输出要进严格
解析器），自由文本则保留最后一个标签之后的内容。

把 `/no_think` 加到用户轮末尾（和任务提示词一样）之后，中英混合那条从 **2103 ms 降到
179 ms**，译文也从"first run green tests"变成"I'll review this pull request later and
run the CI first."——推理不只是慢，它本身在伤质量。

## 10. 日志：这个进程每分钟写 47,000 行

整理历史时每 pool 一个 chunk 就调一次 `NLEmbedding.sentenceEmbedding(for:)`，每次都回到
按需资源框架去找语言数据。5,401 条记录下来，这些查找在五分钟里写了 **140,324 行日志**
（进程总计 236,366 行）。它把口述路径自己的诊断全部淹没——排查插入失败的那一晚，
两次因为这个看不到关键行。

模型加载后不可变，改为按语言只加载一次。之后同样口径：**1,581 行/分钟，其中资源框架
149 行**（原来约 47,300 行/分钟、28,000 行/分钟）。

## 11. 翻译的措辞：提示词能修到哪里（2026-09-21）

用户报的一句原话（原文不在此引用），第一版提示词的输出逐字搬中文语序，读起来不像英语。

改提示词试了四轮，每轮都在同一组句子上实测：

| 句子 | 第一版 | 最终版 |
|---|---|---|
| 用户报的原句（不引用） | 逐字搬语序 | 语序自然，内容完整 |
| 这个方案我们下周一起过一遍 | This plan we will go over together next week. | We'll go over this plan next week. |
| 你那边能不能先把接口文档发我一份 | —（未测） | Can you please send me the interface documentation first, so I can start writing based on that? |
| 明天十点的会我可能迟到十五分钟左右…… | ✅ 完整但语序生硬 | ✅ 完整且自然 |

中间两轮的教训值得记下来：

1. **只要求"自然"，模型会漏内容。** 加了"像母语者那样重组句子"之后，长句里的
   "十五分钟"直接消失了。流畅和完整在 1.7B 上是互相挤压的。
2. **把约束写长，模型两头都丢。** 补上"每个数字/时间/人名都必须出现"之后，长句
   又退回逐字语序。指令越长，小模型越抓不住重点。
3. **一个反例比三段说明管用。** 最终版只有四句话加一个"逐字 vs 正确"的对照例子，
   长句第一次同时做到了完整和自然。
4. **例子不能和测试句重合。** 我一开始拿长句本身当例子，模型直接抄了例子的后半句，
   那一轮的"改善"是假的。

剩下的偏差是模型本身：1.7B 4-bit 在含两个连续动作的短句上仍会丢掉后半个动作。
registry 里目前只有 1.7B；代码里定义了 4B（2.15 GB）但没有下载路径，要不要加是一个
用磁盘和内存换措辞的选择，没有替用户做。

## 12. 指令答案面板

它出现在别的 App 的窗口上方、而用户还在那个 App 里，所以是一块浮层而不是一个窗口：
系统 HUD 材质、圆角、不抢键盘焦点。答案是这块面板存在的理由，所以答案是上面最大的
东西（15pt），产生它的那句话用最小号放在上面——读的人只需要确认自己问对了。

**没有"复制"按钮**：面板出现时答案已经在剪贴板里了，一个重复宣告既成事实的按钮，
只会让人怀疑那件事到底发生没有。剩下的是一行"已复制 · ⌘V 粘贴"，和一个关闭（Esc
同样关闭，点到别处也关闭）。

第一版有个真 bug：先设 `containerSize` 再设 `widthTracksTextView = true`，后者立刻把
容器宽度改回文本视图当时的宽度（0），于是每条答案都被截成一行半，旁边浮着一条滚动条。
现在用 wrapping label 的 `fittingSize` 量，并有三个几何断言守着（短答案不滚动、长答案
撑高面板、超过 320pt 才滚动）。

## 13. 投递：一条路、两个观察值（2026-09-22）

这一节替换了原来的 §13、§14、§15 三节"对齐"。它们记录的是三轮"对齐后修补"，每轮都在同一条回退路径上加一张表；那些表现在全部删掉了，叙事进 git 历史，这里只留契约、证据和删除账本。

### 13.1 两条失败的机制（04:23，Claude 桌面版，光标在输入框里）

日志（用 `/usr/bin/log show` 全路径，避免 shell 别名）：`paste-post-events ms=20` 之后 `paste-confirm ms=7512`，然后 `evidence=value value=changed selection=changed focus=lost`，`inserted=true`。用户看到的是什么都没贴进去、7.8 秒后胶囊说"已输入"。

机制，逐步实测确认：

1. ⌘V 发给 Claude。Chromium 主线程处理粘贴，向剪贴板服务器要字符串；服务器向本应用的承诺式数据提供者要数据，**只能在本应用主线程的运行循环上送达**（实验：后台线程自带运行循环也收不到；主线程被堵时读方 5,004 ms 后拿到 nil）。
2. 与此同时本应用主线程在确认循环里调 `AXUIElementCopyAttributeValue` 问 Claude 的元素——Chromium 要在它自己的主线程上答，而那个线程正堵在读剪贴板上。两边互等，直到 AX 的默认 6 秒消息超时（代码里从未设过超时）。
3. Claude 的读超时拿到空值，什么都没贴。本应用的 AX 读在超时后返回失败，旧元素读不到了，"值变了、焦点丢了"被推断成"已插入"。

根因不是某个阈值，是结构：推断层和观察层并存，而且推断层在粘贴在途时同步调目标进程。

### 13.2 现状为什么会烂（实测，不是推论）

- 近 30 天送达构成：剪贴板粘贴约 89%、辅助功能直写不到 1%，其余为保留或无记录；目标 App 以 Chromium/Electron 类聊天与编辑器为主。AX 直写这条"主路"服务了 0.3% 的口述，却占投递栈 4,546 行的约一半：协调器两次重验证、Codex 专用 DOM class 识别器、"直写无效记忆"、按 Bundle 名匹配的分类表。
- "文字能不能进这里"在四处各有一张表且互相矛盾：服务层 30 个排除角色把 AXTextArea 排除在 App 级粘贴之外，端口层的决策表把 AXTextArea 放行。两套各 146 行的粘贴实现，7 个时间常量，20 种失败原因映射成 5 句胶囊文案。
- `DictationAppModel.swift` 12,045 行、407 个函数、203 个发布属性、无分区；`ContentView.swift` 6,271 行。近 14 天 70 次提交。

### 13.3 契约

新模块 `BestASRDelivery`（650 行，替换 `BestASRInsertion` + `BestASRTextInsertionProbe` 的 4,546 行）：

| 层 | 文件 | 契约 |
|---|---|---|
| Target | `TargetReader` | 读一次"眼前"：前台 App、安全输入、选区（AX 读不到就 ⌘C）、焦点元素显示的文本。每个 AX 调用带 0.25 s 超时。不分类、不记忆。 |
| Deliver | `TextDeliverer` | 唯一进入方式：承诺式粘贴。⌘V 前三个瞬时观察（可发键、目标仍在前台、非密码框）；⌘V 后两个观察，按序：① 应用是否向剪贴板要了文本；② 若应用报了焦点元素且它显示文本，该文本是否变化。在途期间不碰目标。 |
| 判定 | `TextDeliverer.verdict` | 纯函数：`taken && (fieldChanged ?? true)`。 |
| 适配 | `DeliveryInsertionPort` | 状态机的 `captureTarget`/`insert`；自家窗口只在引导练习时算目标。 |
| 结果 | `DictationInsertionFailureReason` | 7 个：nowhere、secureInput、applicationChanged、permissionDenied、nothingToInsert、unavailable、ambiguousReservation。前五个是设计如此，后两个是缺陷。 |

为什么是两个观察值而不是一个：Chromium/Electron 对 ⌘V **无论焦点是否可编辑都读剪贴板**——页面级 paste 事件先取数据再决定要不要用。实测（由正装 App 的探针 `BESTASR_PASTE_PROBE` 发出）：

| 目标 | 焦点 | 承诺被读 | 焦点文本变化 | 判定 |
|---|---|---|---|---|
| 系统设置 | 无输入框 | 否 | — | kept(nowhere) ✅ |
| Chrome，焦点在 `<button>` | 元素不显示文本 | 是（13 ms） | 不可见 | kept(nowhere) ✅（只看承诺会误报） |
| Chrome，`<textarea>` | 显示文本 | 是（18 ms） | 是 | delivered ✅ |
| AXInsertionFixture 可编辑 NSTextView | 显示文本 | 是（21 ms） | 是 | delivered ✅ |
| 微信 | 不报焦点元素 | 是（14 ms） | 无可看 | delivered ✅ |

修复后（两个观察值都在）的同一矩阵，由正装 App 探针实测：

| 目标 | 承诺被读 | 焦点文本变化 | 判定 | 等待 |
|---|---|---|---|---|
| 系统设置，无输入框 | 否 | — | kept(nowhere)，evidence=unread | 400 ms（窗口上限） |
| Chrome，焦点在 `<button>` | 是 | 否 | kept(nowhere)，evidence=read-unchanged | 333 ms |
| Chrome，`<textarea>` | 是 | 是 | delivered，evidence=field | 41 ms |
| AXInsertionFixture 可编辑 NSTextView | 是 | 是 | delivered，evidence=field | 22 ms |

落地的等待是几十毫秒；只有"没落地"才会用满窗口，而那正是要付出等待去确认的情形。

## 14. 交互：按用户实际用到的顺序改（2026-09-22）

用户反馈（归纳）：粘贴瞬间首页闪窗；“在这里试一句”仍是旧界面；首页不应滚动、不应放报错横幅；偶尔松手后没停；活动图悬停无详情；检索是下拉框；设置页配色不一致；文案在解释实现而不是说结果。

| 问题 | 根因 | 改法 |
|---|---|---|
| 粘贴一瞬间首页闪窗 | 主窗口在麦克风关闭后（转写、写入阶段）会渲染"口述输入 / 结束并输入"工作区；口述完成还会在首页放一张"交接卡" | 键盘发起的口述在主窗口里什么都不显示，也不留卡；工作区只给线下录音、内录、导入和从窗口发起的口述 |
| "在这里试一句" | 从首页发起的口述走的是同一套老工作区 | 按钮删除；相关 6 个 UI 测试随之删除，引导页的检查改为"快捷键卡片可见" |
| 首页可滚动、有错误横幅、"最近"卡 | 内容按列表堆叠 | 首页固定一屏：标题、快捷键卡、四个数字、活动图；"没处理完"横幅与"写入失败 N 次"横幅删除（后者整个功能删除），记录在历史页里处理 |
| 松手后没停 | 两条路：释放事件落在"准备麦克风"阶段时被静默丢弃；硬件已松开但事件丢失时看门狗只在"仍按着"时才接管 | 释放等到准备结束再收口（上限 3 秒）；看门狗改为以硬件状态为准，事件没来也算松开 |
| 活动图无详情 | 用的系统 `.help` 提示，一秒后才出且常不出 | 悬停即在图下方写出"M 月 D 日 · N 字"，方块描边 |
| 检索是下拉框 | 日期/状态/App 三个选择器藏在一个菜单里 | 全部可见：日期与状态各一组分段控件，App 一行可点的芯片；去掉"当前筛选"那行冗余标签 |
| 设置页颜色不一样 | 设置用系统分组表单的底色，主窗口用自己的画布色 | 设置的侧栏与表单都用 `BestASRPalette.canvas` |
| 文案 | 到处解释实现和"不会上传" | 首页副标题、侧栏"离线可用 · 不上传"、"N 条本机记录，继续下拉查看更早的"、设置里的四条"不联网/不上传"脚注、"用你自己的模型"、"公开版本号"等全部去掉或改成说结果的话 |

没改的（这轮之外）：事件、人物、历史详情里管理动作的折叠组与"更多"菜单（标准的 macOS 动作菜单，不是筛选）；高级面板的文案；首次设置流程整体（用户说之后再看）。

### 14.1 残余风险（承接 13）

- 剪贴板管理器在 ⌘V 之后读承诺：对报焦点元素的 App 已由第二个观察值兜住；对不报焦点元素的 App（微信）仍可能误报，窗口 400 ms。
- 报了焦点元素但不暴露文本的真输入框（少数 Qt/自绘编辑器）会被判 kept：文字在剪贴板、胶囊说"已复制"，偏向不说假话。
- Keynote 画布、Excel 单元格这类"焦点不是文本但 ⌘V 会落地"的目标同上，判 kept。
