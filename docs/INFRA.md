# 实验室基础设施（Spark 端）

**一句话**：一台 DGX Spark 给一个实验室用，要像一台实验室的服务器那样靠谱：每个人用自己的钥匙进门、只能进自己该进的门；管理员看得到机器健不健康；
一件事换人负责时有交接包；每个共享空间都能加密备份、能恢复；丢了一位管理员的电脑，空间也找得回来；谁也不能一个人占满存储和整理队列。

本文是 Spark 端（本仓库）的做法和接口。Mac 端（设置里的「团队与整理设备」、邀请码、交接包的显示和导出、定时备份）在 Mac 客户端仓库里。
共享空间本身（成员、角色、钥匙、操作日志）见 [SPACES.md](SPACES.md)，隐私承诺见 [PRIVACY.md](PRIVACY.md)。

## 1. 每个人自己的钥匙（队友不再用 Spark 主人的账号）

以前队友连 Spark 用的是 Spark 主人的 SSH 账号：能开 shell，能读主人的文件，能拿到主人的链路令牌。现在：

- **每台成员的 Mac 有自己的 SSH 钥匙**，装在 Spark 主人的 `authorized_keys` 里，但被一条**强制命令**锁住：

  ```
  command="<实例的 zhiji-inbox> bridge <access id>",restrict ssh-ed25519 AAAA… mindloom-member:<access id>
  ```

  `restrict` 关掉端口转发、代理转发、X11、终端和 `~/.ssh/rc`；强制命令不管对方要跑什么，都只跑 `bridge`。
- **bridge 只做一件事**：在这条 SSH 会话的标准输入输出上说 HTTP/1.1，转给本机整理器的私有 Unix 套接字。没有 shell，没有端口转发，
  也连不到别的套接字（套接字路径来自实例自己的包装脚本，不来自对方）。它用 h11（严格的 HTTP/1.1 状态机）逐个解析请求：
  - 只放行 GET / POST / PUT / DELETE，路径只能是成员的路由：`/v1/spaces…`、`/v1/orgs…`、`/v1/access/…`、`/v1/infra/…`；
    个人库、收件箱、开锁和擦除这些路由在这里就被拒（整理器那边再拒一次）；
  - 请求必须带**这台 Mac 自己的成员凭证**（`Authorization: Bearer mlacc1.<这台的 access id>.…`）：主人的链路令牌、别人的凭证都会被拒；
  - 同时带 `Transfer-Encoding` 和 `Content-Length` 的请求直接拒掉，请求体按 h11 解出来的长度重新封装再转发，所以没法夹带第二个请求；
  - 转发时加上**门章**（`X-Mindloom-Gate`：用 `<数据目录>/gate_key` 做的 HMAC，这个文件只有 Spark 主人的账号读得到）。
- **每个人有自己的凭证**，主人的链路令牌从不给别人。整理器只在凭证和同一个 access id 的门章**同时**对上时才认这个成员：
  凭证被偷了，没有那台 Mac 的 SSH 钥匙也用不了；钥匙被偷了，没有凭证也用不了。Spark 上只存凭证的 SHA-256。
- **共享空间照样认签名**：成员进来之后，空间的每个请求、每个操作仍然要那台设备的签名；而且必须是**注册这把钥匙时的那台设备**
  （请求头里的设备、签名操作和加入申请里写的设备不一致就拒：`access_device`）。
- **一个大的长会话就够用**：Mac 跑 `ssh -T <spark> bridge`，保持连接，一个接一个地发请求（keep-alive）。被策略拒掉的请求（403/405）
  不会断开会话；格式不对的请求（400）会断开。空闲 10 分钟会话自己结束。

### 邀请和加入（一次性的邀请钥匙）

1. 管理员的 Mac 生成一对临时 ed25519 钥匙和 32 字节密码，把**公钥**和 `SHA-256("mindloom-access-ticket-v1\n" ‖ 密码)` 登记到 Spark
   （`POST /v1/access/tickets`，最多 7 天有效）。Spark 在 `authorized_keys` 里加一行，强制命令是 `enroll <ticket id>`。
   临时**私钥**和密码放进邀请码，和共享空间的邀请放在一起（Spark 从头到尾见不到私钥）。
2. 受邀的 Mac 用这把临时钥匙连上来，只能跑 `enroll`：它在标准输入里交一个签了名的 JSON——它**自己新生成的** SSH 公钥、成员编号、
   设备的两把公钥（用设备签名钥匙签名，证明钥匙在它手里）和密码。参考实现：`organizer.access.enroll_request`。
3. Spark 核对密码（错 10 次锁死）、签名、设备编号没有被别的钥匙占用，然后**在原地**把邀请那一行换成成员那一行，返回一次性的凭证
   （`mlacc1.<access id>.<32 字节 base64url>`）。邀请钥匙从此失效。
4. 之后这台 Mac 用自己的钥匙走 bridge，按 [SPACES.md](SPACES.md) 发加入申请，管理员同意后它就是空间成员了。

谁能发邀请：Spark 主人（链路令牌），以及经 bridge 进来、在这台 Spark 上管理某个**组织**的成员。只管理一个空间不够（任何队友都能自己建一个
空间，复查 V8R-06）：空间管理员只能把**已经接入**这台 Spark 的人拉进自己的空间；Spark 主人可以用 `ORGANIZER_SPACE_ADMINS_INVITE=1`
放开。**一个人的第二台 Mac**：由他已有的那台 Mac 发一张 `kind: "device"` 的邀请（只能绑到他自己的成员编号；每人最多 4 台），
新 Mac 加入后由旧 Mac 在空间里签 `device.add`。

兑换时还有两条（复查 V8R-07、V8R-08）：

- 一张「新成员」邀请只能用一个**这台 Spark 还不认识的成员编号**，或者这个编号已经绑定的那把设备钥匙；拿别人的编号（比如 Spark 主人的，
  在每个名单里都看得到）来兑换会被拒（`member_id_taken`）。同一个人的其他 Mac 走设备邀请。
- 被断开过的设备编号不能再兑换任何邀请（`device_revoked`）：它还在原来那些空间的名单里，再接入就等于不经空间同意回到空间。这台 Mac
  要换一把新的设备钥匙重新接入，再由各个空间重新同意。

### 一个人的几台 Mac、添加组织管理员（v8 合同 C 第 4 条，控制台用）

- **一个设备编号只属于一个成员**：空间、组织和这里的访问记录合在一起看。兑换邀请时设备已经在别人名下（`device_member_conflict`），
  空间里 `device.add`、加入申请、`org.admin_add`、`org.device_add` 也一样；经 bridge 进来的 Mac 只能以自己的成员编号签操作（`access_member`）。
- **第二台 Mac**：设备邀请兑换后，访问记录就把它绑到同一个成员编号上。第一台在每个空间签 `device.add`（把当代空间钥匙封给它）、
  在它管理的每个组织签 `org.device_add`；第二台也可以拿邀请码直接加入这个成员还没进过的空间。断开过的 Mac 不会再被加回任何空间或组织（`device_revoked`）。
- `GET /v1/access/devices[?member_id=]`：一个成员的每台 Mac——访问状态（指纹、最后出现时间）、它在哪些空间和组织里、状态——以及要签的清单：
  还连着的 Mac 有 `to_add: {spaces, orgs}`（它的成员在、它还不在的空间；成员管理、它还不是组织设备的组织），断开了的 Mac 有
  `to_remove: {spaces, orgs}`（它还是成员设备的空间、还是组织设备的组织：在那里签 `device.remove`（同时换钥匙）和 `org.device_remove`）。
  成员看自己；组织管理员看他组织里的人（组织空间的成员和组织管理员）和他邀请来的人（还没进任何空间的新成员也看得到）；
  Spark 主人看任何人（要给 `member_id`）。只管理一个空间的人看不到别人的（复查 V8R-06）。只有编号、公钥和状态。
- **添加组织管理员**是组织的签名操作 `org.admin_add {"member_id","device"}`：`device` 必须是这个人在这台 Spark 上自己用着的 Mac（他在某个
  空间里的设备，或访问记录里他的 Mac；这台 Spark 还不认识的人照旧可以直接加），否则 `unknown_member_device`。之后他名下的其他 Mac 由他自己
  `org.device_add`。新管理员的设备出现在每个组织空间 `escrow.missing` 里，管理员的 Mac 用 `escrow.wrap` 把当代钥匙补封给它。
- `org.device_remove {"device_id"}`：退掉一台组织设备（不能退签名的这台）；它靠托管知道当代钥匙的组织空间进入「待换钥匙」。结果的 `effects`
  里有 `rotation_pending` 和 `still_member_in`。

### 断开一台 Mac

`DELETE /v1/access/members/{access_id}`：Spark 主人可以断开任何一台；成员可以断开自己的 Mac；**组织管理员**可以断开他组织里的人和他邀请来的人的 Mac。
空间管理员不能把别人从整台 Spark 上断开（他把人从自己的空间移除就够了；复查 V8R-06：任何队友都能建个空间、邀请组织管理员进来，再把他断开）。
那一行从 `authorized_keys` 里删掉，**文件和发邀请之前逐字节相同**（包括原来最后一行没有换行符的情况：当初为了接上一行补的换行会被拿回去，
只要文件其余部分没被别人改过）；凭证的哈希立即删除，所以即使还开着的 bridge 会话，下一个请求也会被拒（401）。没用掉的邀请到期后自动删掉那一行。

断开访问和退出空间原来是两件事，现在连在一起（复查 V8R-07）：

- 断开之后，Spark 在**每个**空间和组织里都拒绝这台设备（读、写、签操作都拒，`device_revoked`），不管它从哪条路来；它也不能再兑换邀请。
- 发起断开的 Mac 在显示「已断开」之前，就在它能签名的每个空间里签 `device.remove`（换钥匙）、在它管理的组织里签 `org.device_remove`；
  它签不了的空间留在 `to_remove` 清单里，由那里的管理员处理（控制台会列出来）。换钥匙之后，这台设备手里的旧钥匙打不开以后的新内容。

### 经过中继的 Spark

如果 Spark 只能经过一台跳板机（ProxyJump）访问，成员在跳板机上也要一行只能转发到 Spark SSH 端口的受限钥匙，用和手机相同的
`spark/relay-authorize`（`add <id> <spark host> <port> ssh-ed25519 <base64>` / `remove <id>` / `list`；标记写成 `mindloom-phone:<id>`）。
只有 Spark 主人的 Mac 能改跳板机，所以由它对账（复查 V8R-12）：跳板机上的团队行（`team-<公钥 SHA-256 前 12 位>`）始终等于
「每张还没用的邀请的临时钥匙 + 每台在用的 Mac 自己的钥匙」，`GET /v1/access/tickets` 和 `GET /v1/access/members` 只对 Spark 主人给出这些公钥
（`ssh_key`）。邀请用掉、到期、作废，或者一台 Mac 被断开，它那一行就从跳板机上删掉，跳板机的 `authorized_keys` 回到发邀请之前的样子；
成员的 Mac 在跳板机上先出示自己的钥匙，邀请钥匙只在自己那一行还没加上的那段时间里用。

## 2. 管理控制台看到的 Spark 健康

`GET /v1/infra/health`（Spark 主人，或经 bridge 进来的组织管理员；只管理一个空间的人不行，复查 V8R-06）：

- **整理器**：版本、部署的提交号、运行时长、个人库锁没锁、队列长度、最近一次错误的类型（锁着时不给）、共享空间数、组织数、开着的空间整理库、
  空间队列总长、访问的人数 / 台数 / 未用的邀请数；
- **模型服务**：整理用的对话模型、向量模型（以及配置了的读图模型）：在不在线、模型名、端口、响应毫秒数（只探本机回环地址）；
- **GPU**：型号、利用率、温度、功耗、显存。DGX Spark（GB10）的 GPU 和系统共用内存，`nvidia-smi` 显存一栏是 `[N/A]`，这时给出
  统一内存的总量和可用量（来自 `/proc/meminfo`）以及所有 GPU 进程占用之和（只给总和，不列进程）；
- **磁盘**：数据目录所在磁盘的总量、剩余、剩余百分比，数据目录和共享空间目录各占多少字节；
- **warnings**：`chat_down`、`embed_down`、`disk_low`（剩余不到 5%）、`memory_low`（可用统一内存不到 2 GiB）。

只有数字和状态：没有任何素材、事件、名字、文件路径或别人的进程。每项探测都有短超时，结果缓存 15 秒。Spark 主人**个人库**的那一项
（锁没锁、队列长度、最近的错误）只给主人：组织管理员看不到主人的 Mac 什么时候连着、整理了多少（复查 V8R-14）。

成员和设备、他们的角色、组织管理员、组织审计记录这些，管理控制台从 `GET /v1/access/members`、`GET /v1/access/audit`、
`GET /v1/orgs/{id}`、`GET /v1/orgs/{id}/audit` 和每个空间的 `GET /v1/spaces/{id}` 拿到——也都只有编号、时间和动作，没有内容。
Agent 的访问在 Mac 上授予和收回（见 Mac 端），Spark 上只有它们读空间时留下的 `agent.access` 记录。

## 3. 交接：转交负责人和交接包

- **转交负责人**是共享空间里的一条签名操作 `matter.handover`（负责人自己或维护者可以做），可以附上交接包那条快照素材的编号
  （`pack_item_id`，必须是这个空间里的一条 `snapshot` 素材）。
- **生成交接包**：`POST /v1/spaces/{id}/organizer/handover-pack {"matter_id", "from"?, "to"?}`（贡献者以上；个人空间是
  `POST /v1/events/{id}/handover-pack`），排队，整理器下一步就写；`GET …/handover-pack/{pack_id}` 取结果。
  交接包由技能 `handover-pack`（[skills/handover-pack/SKILL.md](../skills/handover-pack/SKILL.md)）写：现在到哪了、谁还欠着什么
  （谁答应了谁、哪天前、兑现了没有）、截止日、已经定下的事（带原话）、还没答案的问题、先看哪几条素材、接手先做什么——**每一句都带出处素材**，
  原话必须逐字。返回结构化的交接包和一份 Markdown（带占位符，Mac 放回原号码后导出，或者作为快照素材分享进空间）。
- 交接包存在加密的整理库里；它引用的任何一条素材被删除或撤回，整份交接包随之删除。

## 4. 备份和恢复

- **导出**：`POST /v1/spaces/{id}/backup`（空间管理员的设备签名），请求体 `{"backup_id", "epoch", "key"}`。`key` 是管理员的 Mac 为这一份备份
  新生成的随机钥匙，只借给这一次导出；Mac 把它分别封给这个空间每位管理员的设备（组织空间还有组织管理员的托管设备），封好的钥匙放在备份旁边的
  回执里（复查 V8R-13：备份里有只有管理员能看的东西——下架理由、成员各自的隐藏、审计、加入申请；所以普通成员即使拿到空间钥匙和备份文件也打不开）。
  更早的备份用 `HKDF-SHA256(ikm = K_epoch, salt = backup_id 的 16 字节, info = "mindloom-space-backup-v1")` 派生的钥匙，Mac 仍然认。
  返回的是一条流（`MLBK1`）：一个小的明文头（空间编号、备份编号、代数——用来知道拿哪把钥匙开），后面全是 ChaCha20-Poly1305 加密的帧，
  最后一帧带结束标记。里面是这个空间在 Spark 上的全部：签名的操作日志、钥匙包、代际链、素材钥匙、托管钥匙包、邀请、加入申请、下架、
  提议、审计记录，组织空间还有组织的记录，原件密文，以及空间整理库（SQLCipher 文件）和它的钥匙编号文件。快照是在空间的锁里取的，
  行、原件和整理库彼此一致。
- **谁打得开**：这个空间的管理员和组织管理员（各用自己设备上的封装）；普通成员和 Spark 自己都打不开放在管理员 Mac 或移动硬盘上的备份。
  回执里只有编号、数量、大小、摘要和封好的钥匙，不写空间名字，文件名也不带空间名字（`mindloom-<日期>-<编号前 8 位>.mlbk`），只有本人可读。
- **定时备份**由管理员的 Mac 安排（每天或每周拉一次，存到它自己或移动硬盘）。每次导出都是完整的一份。
- **恢复**：`POST /v1/spaces/{id}/restore`，请求体就是备份流，`X-Mindloom-Backup-Key` 放钥匙，`X-Mindloom-Restore` 放
  `{"mode": "new" | "replace", "purge": [素材编号…], "force"?: true}`。谁能恢复：Spark 主人（新的或重装过的 Spark），或经 bridge 进来、**此刻**在这台
  Spark 上是这个空间管理员的人（空间的数据坏了）。**读请求体之前**就先查完（复查 V8R-10）：经 bridge 来的人必须是这台 Spark 上已有的这个空间的
  管理员，声明的长度不能超过 `ORGANIZER_MAX_RESTORE_MB`（默认 8192），磁盘要放得下两倍的大小外加 1 GB 余量；没有声明长度的请求体边收边数、边看磁盘。
  然后 Spark 把流解到一个私有的临时目录：
  - 钥匙不对、改了一个字节、截断了、后面多了东西、是别的空间的备份——都拒（`bad_backup`）；
  - **每一行都属于这个空间**（组织的行属于它的组织）：备份里夹带别的空间或组织的行，整份拒掉（复查 V8R-01：之前一位队友恢复他自己的空间时，
    可以往别人的空间里写一行「管理员」）；
  - **重放签名日志**：从第一条（创建者自己签名）开始，每条操作都必须由日志自己接纳过的设备签名（`join.approve`、`device.add`、
    托管接管 `space.recover` 由组织日志里的管理员设备签名；这台 Spark 已有这个组织时，用的是它**自己的**组织日志，不是备份里的；组织空间的
    第一条必须由组织管理员的设备签），加密字段必须和操作里承诺的哈希一致，序号不能有缺口；
  - **决定权限的行不能超出日志**：空间那一行（拥有者、组织、规则、代数、归档）、成员（角色、状态、外部合作者）、设备（公钥、状态）和钥匙包，
    都和日志重放的结果对照，只能比日志更严（组织管理员被移出组织时 Spark 自己降过的角色），不能更宽：多一个成员、抬高角色、把移除的人变回来、
    改规则（比如把配额改成不限）、把代数往回改——都拒。组织的行（只在这台 Spark 还没有这个组织时才写）同样对照组织日志；
  - **日志的新旧决定写什么**（复查 V8R-03）：这台 Spark 上已有这个空间时，比较两份日志——
    - 这台 Spark 的日志**已经包含**备份的日志（一样长，或者更长：备份之后又有人被移除、换过钥匙、撤回过素材）：**一行都不动**，只补回数据——
      还在空间里的素材的原件密文丢了或坏了就换回来，整理库丢了就放回（之后撤回或移除的素材排进它的清除队列，下一次租约时执行）。
      结果里 `"applied": "fill"`。所以恢复一份旧备份不会让被移除的人回来，也不会把钥匙退回到他手里的那一代；
    - 这台 Spark 的日志是备份日志的**前一段**（它丢了后面的部分）：用备份整份替换（`"applied": "full"`）；
    - 两份日志**对不上**：拒（409 `log_diverges`）；只有 Spark 主人可以加 `"force": true` 强行覆盖，成员的 Mac 之后会发现日志变了，
      把它记得已被移除、却又回到名单里的人再次移除（换钥匙），在那之前不发新的共享；
  - 备份之后才被撤回或移除的素材，恢复它的 Mac 从自己保存的日志里知道，放在 `purge` 里，恢复后立即再清除一次（留一条 Spark 的
    `system.remove` 记录）。
- **恢复演练**是测试的一部分（`spark/tests/test_backup.py`）：导出 → 恢复到一台全新的 Spark → 每个成员读到的东西和之前一模一样（操作日志、
  钥匙、素材、原件、整理库里的事）→ 撤回的仍然撤回、移除的成员仍然进不来 → 新 Spark 上照常共享和换钥匙 → 数据目录里扫不到明文。

## 5. 组织钥匙托管：丢了一位管理员也能找回空间

- 组织的规则 `recovery_admins`（1、2 或 3）：组织空间**每一代**的钥匙，必须至少能被 `min(recovery_admins, 现有管理员人数)` 位组织管理员
  **用他自己的组织设备**打开——要么他本来就是成员（成员钥匙包），要么另有一份**托管钥匙包**（和成员钥匙包同样的封法，封给他的组织设备）。
  建空间、移除成员、退役设备、换钥匙时，Mac 要一起交上托管钥匙包（`escrow_wraps`），不够就拒（`escrow_required`，并列出还缺哪些设备）。
  新加了一位组织管理员，或者把规则调高之后，持有钥匙的管理员的 Mac 用 `escrow.wrap` 补上；`GET /v1/spaces/{id}` 和组织概况里的
  `escrow` 会显示还缺谁。
- **找回**：一位组织管理员用 `GET /v1/orgs/{id}/escrow` 取到他的托管钥匙包，在自己的 Mac 上打开，签一条 `space.recover`
  （用他的组织设备签名、写明这台设备自己的两把公钥）。他就成了这个空间的管理员成员，托管钥匙包成了他的成员钥匙包，不需要任何空间成员在线。
  之后照常：用 `member.remove` / `device.remove` 带着新钥匙把丢失的那台移出去。成员的 Mac 只在对照**组织自己的签名日志**
  （`space_member.org_roster`）确认签名的是一位在任的组织管理员时，才承认这次接管。
- 一位组织管理员被移出组织时，他的托管钥匙包全部删除；如果他只是凭托管知道某个空间的当代钥匙（不是成员），那个空间进入「待换钥匙」，
  换钥匙之前不收新共享。这就补上了 v7 复查的 V7-S7：唯一的空间管理员离开或丢了电脑，组织里另一位管理员能接管。
- 这是一项权力，要说清楚：在 `recovery_admins` ≥ 1 的组织里，**组织管理员能打开组织的任何空间**（GitHub 上组织所有者也能进组织的任何仓库）。
  个人拥有的小组空间没有托管。

## 6. 配额和公平

- **存储配额**：每个成员在每个空间里一份配额，算他的原件密文（未认领的上传也算）和他的操作里还在的加密字段。`ORGANIZER_MEMBER_QUOTA_MB`
  （默认 2048）是 Spark 主人定的**上限**，空间规则 `member_quota_mb` 只能往下调（0 或不设就是上限本身；设得比上限大也按上限算，复查 V8R-09：
  之前任何队友建个空间、把配额设成 0 就能写满主人的磁盘）。另外每个成员在整台 Spark 上所有空间加起来有一个总量（`ORGANIZER_MEMBER_TOTAL_MB`，
  默认 8192），一个成员编号最多建 `ORGANIZER_MAX_SPACES_PER_MEMBER`（默认 30）个空间（409 `too_many_spaces`）。超了就拒（413 `quota_exceeded`，
  附已用和上限，整台 Spark 的总量超了时带 `scope: "spark"`）；撤回、移除会把空间还回来。`GET /v1/spaces/{id}` 的 `me.usage` 是自己的用量，管理员还能看到每个成员的 `usage_bytes`。
- **轮流整理**：共享空间的整理队列不再只按时间排：同等紧急程度下各成员**轮流**（最久没轮到的先，每个人自己的素材仍按时间顺序），
  一个人一下子导入几百条，也挡不住别人的新素材。
- **截止近的先整理**：一件事的卡片上有还没办完、日期在 `ORGANIZER_DEADLINE_DAYS`（默认 7）天之内的事实，或者它的线索图上有这样的截止 / 承诺，
  这件事就算紧急：它的素材（以及同一个成员同一包里的其他素材）先整理，它的卡片先重写，它的图先画。
- 个人空间只有一个人，队列保持原来的时间顺序。每个空间的整理器各有自己的线程，模型服务那边自己批处理并发请求。

## 诚实的边界

- 门章证明请求经过了这台 Spark 主人账号下的程序，不是别的 Unix 用户发来的；Spark 主人自己当然什么都能做（他本来就能读整个数据目录）。
- 成员的钥匙装在主人的 `authorized_keys` 里，由主人账号下的进程执行强制命令：Spark 主人仍然是这台机器的管理员。真正的多租户
  （每人一个系统账号）需要 sudo，不在这次范围内。
- bridge 一次处理一个请求；需要并发的 Mac 可以开两条会话。
- 备份是完整的一份，不是增量。恢复一份比 Spark 现有日志旧的备份只补数据、不回退（见第 4 节）；Spark 的日志整份丢失或被主人强行覆盖时，
  之后才发生的操作只能由成员的 Mac 按自己保存的日志补救（自动补「撤回 / 移除」，管理员的 Mac 把又回到名单里的人再次移除）。
- 被断开的 Mac 在空间名单里待到有人签 `device.remove`：在那之前 Spark 已经哪里都不让它进，但它手里还有断开之前的钥匙（打不开换钥匙之后的内容）。
- 托管让组织管理员能打开组织的任何空间（这是规则本意）；个人小组空间没有托管，唯一的拥有者丢了所有设备，空间就打不开了。
- 配额只算 Spark 上这个成员的密文和加密字段；空间整理库的大小不分摊到人。
- 交接包由本地模型写，可能漏掉事情；每一句都有出处，接手前请和原负责人核对。
