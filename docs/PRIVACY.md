# 隐私

**一句话**：你的 Mac 是保险箱，也是唯一的原件所在。Spark 是一张工作台：它只拿到整理需要的东西，用一把只在你 Mac 上的钥匙锁着，原件读完就删，你让它忘掉，它就忘掉。

## 为什么「模型在本地跑」还不够

一台 DGX Spark 通常是一个团队、一个实验室或一个组织共用的。「模型在本地跑」只回答了谁在算，没有回答在这种场景下真正要紧的问题：

- 什么东西放在哪台设备上？
- 什么东西会经过链路，经过之前有没有处理过？
- 同一台 Spark 上的其他人能不能读到？
- Spark 会不会一直留着？
- 我能不能收回？
- 做了这些以后，存储会不会膨胀，整理效果会不会变差？

织机按下面七条来回答；手机这一端另有五条（见[「手机」](#手机)）。每一条都在代码里做到，并且有测试。Spark 端的测试在 `spark/tests/test_privacy.py`、`spark/tests/test_privacy_review.py` 和 `spark/tests/test_privacy_fixes.py`（手机部分在 `spark/tests/test_phone_link.py`），下文括号里是测试名；Mac 端的测试在 Mac 客户端仓库的测试目录里。2026-09-30 做过一轮对抗式复查，查出的问题和改法见文末「复查之后」。

## 七条保证

1. **什么放在哪，一清二楚。** 原件都留在 Mac 上：录音、声纹、词典、你放进来的原始文件、全分辨率截图。整理好的结果回到 Mac，也存在 Mac 上。Spark 上的东西随时可以清空，再从 Mac 重建。
2. **号码先遮住再出门。** 离开 Mac 之前，整理用不着的号码会换成固定的占位符，比如手机号、邮箱、身份证号、银行卡号、验证码、密码、密钥和令牌、IP 地址、车牌号。截图发出去的那一份，同样的号码会被涂掉。结果回来后，Mac 再把原文放回去。人名、日期、金额、地点都保留，因为整理需要它们。
3. **Spark 上的东西都锁着。** Spark 存的一切都加密（SQLCipher）。钥匙只在你的 Mac 上（钥匙串），只经你自己的 SSH 隧道进到整理进程的内存里，从不写盘，也从不进日志。同一台 Spark 上的其他人只能看到密文。Spark 重启以后，在你的 Mac 重新连上之前，谁也读不出来。
4. **读完就删。** 图片和文件的字节在 Spark 读完之后立刻删除，只留下读出来的文字，而且文字也已经遮过号码。手机分享的内容，Mac 取走后就删掉。
5. **你能收回。** 在 Mac 上删掉一条，Spark 上也跟着删；链路断开期间攒下的删除，一连上就先发。关掉链路，Spark 上的库随即锁上。「让 Spark 忘掉我的内容」会清空 Spark 上的一切，并销毁 Mac 上的那把钥匙。
6. **不拿功能换隐私。** 口述、录音、识别、插入、搜索，从来都不经过 Spark。链路关着的时候，Mac 自己在本机整理。
7. **存储不会膨胀。** Mac 上，同样的文件只存一份（按 SHA-256 内容寻址）。Spark 上只剩文字，下面有实测的每千条素材占用。

## 一张表：放在哪、经过什么、谁能读、怎么收回

| 东西 | 放在哪 | 经过链路的是什么 | 同一台 Spark 上谁能读 | 怎么收回 |
|---|---|---|---|---|
| 录音、声纹、词典 | 只在 Mac | 从不发送 | 没有人（Spark 上没有） | 在 Mac 上删 |
| 文字：口述、会议逐字稿、粘贴的聊天和邮件 | Mac 存原文 | 遮过号码的文字 | 库是密文；只有开着锁时的整理进程，和它调用的模型服务（看得到遮过号码的提示词） | Mac 上删一条，Spark 跟着删；关链路即上锁；「忘掉我」清空 |
| 截图、图片、文件 | Mac 存原件 | 号码涂掉、去掉元数据的副本；音视频从不作为字节发送 | 读完就删字节，只留遮过号码的文字（加密） | 同上 |
| 整理结果：事件、现状、人物、首页排序 | Mac 存一份（号码还原成原文） | 从 Spark 回来 | 加密；开着锁时只有整理进程 | 「忘掉我」清空后可从 Mac 重建 |
| 手机上说的话、分享的东西 | Mac 取走后保存 | 在手机上就封好，只有你的 Mac 能打开 | 没有人：Spark 只转交密文，没有能打开的钥匙 | Mac 取走即删；「断开 iPhone」吊销手机的钥匙 |
| 钥匙 | Mac 的钥匙串 | 开锁时经你自己的 SSH 隧道发一次 | 只在整理进程内存里；不写盘、不进日志；进程不可转储 | 关链路、Mac 睡眠或退出、10 分钟没有请求，Spark 都会上锁；「忘掉我」销毁钥匙 |

「同一台 Spark 上谁能读」有一个前提：**整理服务用一个只有你自己用的系统账户跑**。能以同一个账户运行程序的人可以冒充整理服务骗到钥匙，这台 Spark 的 root 也能读进程内存（见[诚实的边界](#诚实的边界)）。

## 每一条怎么做到

### 1. 什么在哪里

| 数据 | Mac | 经过链路 | Spark |
|---|---|---|---|
| 录音、声纹 / 说话人向量、词典、窗口和会议标题 | 保存 | 从不发送，发送类型里没有这些字段 | 没有 |
| 逐字稿、分段、你粘贴或拖进来的文字、文档读出的文字 | 保存原文 | 遮过号码的文字 | 加密保存遮过的文字 |
| 截图和图片 | 保存原件 | 缩小、去掉全部元数据、号码涂掉的副本 | 读完即删，只留遮过号码的读图文字 |
| Mac 读不出文字的文档（xlsx、pptx、Keynote 等），扫描版 PDF，带图的 Word | 保存原件 | 重做的发送副本：里面的图片涂掉号码，音视频和嵌入对象清空 | 读完即删，只留遮过号码的文字；图片只在 Mac 标明「已涂过」时才读 |
| 音频、视频，以及压缩包里的音视频 | 在 Mac 上转成文字 | 从不作为字节发送 | 没有 |
| 整理结果（事件、标题、现在到哪一步、排序、提问） | 保存，号码还原成原文 | 从 Spark 返回 | 加密保存 |
| 手机键盘说的话、手机分享的内容 | 取走后打开、保存 | 在手机上封好（只有你的 Mac 能打开），经你自己的 SSH 密钥进 Spark 收件箱 | 只存封好的密文，打不开；Mac 取走即删 |
| 手机上说话的声音 | 没有 | 从不发送 | 没有（只在手机内存里，识别完就丢） |
| 钥匙 | 钥匙串 | 只在解锁时经 SSH 隧道发一次 | 只在进程内存里 |

Spark 上没有任何东西是唯一的一份。「让 Spark 忘掉我的内容」之后，Mac 把之前送达过的素材标成未送达，按原来的规则重新送；Spark 上的整理结果会重新生成（`test_wipe_needs_the_matching_key_id_and_forgets_everything`）。

### 2. 遮号码

规则是 Mac 和 Spark 共用的一份规范。两边用同一组测试向量（`privacy/mask_vectors.json`），文件的 SHA-256 写死在两边的测试里，谁改了都会立刻失败（`test_mask_vectors_are_the_shared_file_and_all_pass`）。

| 原文里 | 发出去的是 |
|---|---|
| 手机 138 1234 5678 | 手机 〔手机号·xxxxxx〕 |
| 邮箱 li.mu@example.com | 邮箱 〔邮箱·xxxxxx〕 |
| 验证码 482913 | 验证码 〔验证码·xxxxxx〕 |
| 周五下午三点在图书馆二楼，报价 1,280 元 | 原样不动 |

- `xxxxxx` 由一把只属于你这个资料库的遮号钥匙算出来。同一个号码在你的资料库里永远是同一个占位符，所以整理时仍然看得出「两条素材提到的是同一个手机号」。换一个资料库，占位符就完全不同。
- 遮号码可以重复做：已经遮过的文字再遮一次，结果不变。
- Spark 自己也遮一遍。从图片和文件里读出来的文字（读图结果、文档正文和概要、字段），在存盘或放进任何提示词之前先遮；Mac 发来的文字再遮一遍，作为纵深防御。每次模型调用的输出记录也一样（`test_text_read_from_bytes_and_incoming_text_are_masked_before_storage_and_prompts`、`test_masking_is_idempotent_on_what_the_mac_already_masked`）。
- 会看到占位符的 Skill（十个里读素材文字的九个，加上 recall），说明里都写了一句：「占位符（如〔手机号·a1b2c3〕）是被遮住的号码，原样保留，不要猜、不要改写。」（`test_skills_that_see_masked_text_say_placeholders_stay_as_they_are`）
- **模型改坏的占位符当场修好。** 模型偶尔把抄来的占位符写坏，例如把〔验证码·3feb18〕写成「邮箱验证码3feb18」：括号和「·」没了，Mac 还原不了，会显示一串像验证码的字符。现在每个 Skill 的输出在校验和存盘之前都先过一道确定性的修补：这次调用的输入里出现过的占位符，它的 6 位编号如果出现在完整的〔标签·编号〕之外，就连同残留的标签、「·」和括号改回完整的占位符；输入里没有的编号不动，也不会凭空造出占位符；两个号码碰巧同一编号时，只有残留的标签说得清是哪一个才修（`masking.repair_placeholders`；`test_the_organizer_stores_the_repaired_gist`、`test_the_broken_forms_seen_and_their_neighbours_are_rewritten_to_the_input_placeholder`）。
- **规范第 3 版**：遮号评测里漏掉的一处是聊天里后说出来的验证码（「……短信验证码刚刚发过来了，我收到的是 2802」）。第 3 版加了一条规则：「验证码」这类词之后、同一句话里（40 个字以内，中间没有句号、问号、叹号、分号、换行和数字），在「是」「为」、冒号或 is 之后出现的 4–8 位数字也遮住。共享向量 200 条（新增 8 条要遮的和 6 条不能遮的）；在本仓库全部合成场景的文字上，这条新规则一处也没有命中，所以已有的整理结果不变。
- **遮号会不会影响整理效果**：用 `eval/privacy/` 里的工具（号码压力集生成、遮号开关对照、成对调用、还原检查、向量相似度）在同一套数据上比较过遮号和不遮号（规范第 1 版，Qwen3.6）。在留出集里写进 37 处合成号码的压力集上各跑 5 次，B³ F1 不遮号 0.788 ± 0.038、遮号 0.788 ± 0.013；而输入逐字节相同的对照组，两组之间自己就差 0.038。在完全相同的上下文里把含占位符的调用再发两次，归事件的决定和原文版本相同 105/111、和原样再发相同 104/111：遮号造成的差别和服务器自己的波动一样大。占位符不会让不相干的素材在检索上变得更像。代价是：号码本身就是事情内容时（换号、换邮箱），结果里偶尔少写一个号码（原文仍在 Mac 上）。数字和出处见 [EVALUATION.md §11](EVALUATION.md#11-隐私) 和 `eval/results-2026-09-30/eval.json` 的 `masking_eval`。

### 3. 锁着存

- **钥匙**：Mac 第一次打开链路时，为这个资料库生成一把 32 字节的随机钥匙，存进钥匙串。经过链路的只有这一把；Spark 用它推出两把子钥匙：一把打开加密库，一把算占位符。Spark 磁盘上跟钥匙有关的只有一个 16 位的钥匙编号（`store.keyid`，权限 0600），用来在锁着的时候说明「这个库属于哪把钥匙」，从编号推不出钥匙。
- **加密**：整理库 `organizer.db` 用 SQLCipher 4 加密：数据页、WAL 日志、回滚日志全是密文。没有钥匙打开，只会得到「不是数据库」（`test_no_plaintext_and_no_key_on_disk`：通过接口写进一段哨兵文字、一张截图、一个文档，再逐字节扫描数据目录里的每个文件，哨兵文字、各种形式的钥匙都找不到，锁上之后再扫一遍也一样）。
- **开锁和上锁**：服务启动时是锁着的。Mac 连上以后，第一个数据请求就是开锁；关掉链路时先上锁再拆隧道。锁着的时候，除了健康检查、开锁、上锁、清空和手机收件箱的「放进来」，每个数据接口都回答 423；后台整理暂停，开锁后接着做（`test_every_data_route_is_423_while_locked_but_health_and_phone_add_work`、`test_worker_pauses_while_locked_and_resumes_after_unlock`、`test_unlock_lock_health_and_stats`）。
- **钥匙不对**：用别的钥匙来开，回答 409，同时给出磁盘上的钥匙编号，库保持锁着；Mac 这时提示「Spark 上的内容属于另一把钥匙」，并提供「让 Spark 忘掉旧内容」（`test_wrong_and_malformed_keys`）。
- **从旧版本升级**：以前的明文库在第一次开锁时整库加密，随后删掉明文文件（`test_legacy_plaintext_store_is_encrypted_on_first_unlock`）。
- **光有令牌读不到**：链路令牌是 Spark 账户下的一个文件，同一账户下的程序都能读到它。所以 Mac 开锁之后，每个数据请求还要带一个从钥匙推出来的访问凭证（`X-Mindloom-Access`）；只拿令牌来读，回答 403（`test_after_the_macs_unlock_data_routes_need_the_key_derived_access_proof`）。
- **Mac 不在就自己锁上**：Mac 连着时每隔几秒就会来取一次状态。超过 10 分钟没有来自 Mac 的数据请求（Mac 退出、睡眠、崩溃或断网），Spark 自己上锁；Mac 下次连上时重新开锁（`test_a_store_the_mac_unlocked_locks_itself_when_the_mac_stops_asking`）。Mac 睡眠和退出时也会主动先上锁，上锁没成功会再发一次。
- **后台任务只在开着锁的时候跑，写入绑在这一次开锁上**：整理素材、定期整理事件（event-consolidate）、人物整理（person-resolve）、画线索图（matter-map）和把事搓成绳（matter-group）都在后台 worker 里，库锁着时一概不跑。它们发给模型的每个调用（包括并发的调用）都绑定发出时的那一次开锁：调用还在路上时库被锁上，或者「忘掉我」之后又用新钥匙开了新库，调用回来时什么都写不进去（`test_a_model_call_in_flight_during_wipe_writes_nothing_into_the_next_store`、`test_a_consolidation_call_in_flight_during_forget_writes_nothing_into_the_next_store`、`test_a_person_resolve_call_in_flight_during_forget_writes_nothing_into_the_next_store`、`test_a_lock_during_a_pass_writes_nothing_and_the_pass_runs_again_after_the_next_unlock`、`test_a_map_call_in_flight_during_forget_writes_nothing_into_the_next_store`、`test_a_lock_during_a_grouping_call_writes_nothing`）。它们放在内存里的东西（事件的标题和样例、人名索引）随上锁、清空一起丢掉。
- **不留转储**：整理进程启动时把自己设成不可转储（`PR_SET_DUMPABLE=0`），核心转储上限设为 0：它崩溃时不会把内存里的钥匙和文字写进系统的崩溃目录，同一账户下的程序也读不了它的内存（`test_process_hardening_sets_a_hard_zero_core_limit_and_turns_dumping_off`）。

### 4. 读完就删

- 读图（image-read）和读文件（file-read）把读出的文字存下来的那一个事务里，同时删掉图片或文件的字节。读失败、重试也用完了，字节同样删除，这一条标成「读不出」（`test_read_then_delete_leaves_no_blob_bytes`、`test_a_read_that_fails_for_good_deletes_the_bytes_and_marks_the_item_unreadable`）。
- 文档和压缩包里的音频、视频，Spark 从不解码、从不转写。解析器跳过它们，只记一句「N 个媒体附件未读取（只在 Mac 上）」，连文件名都不列（`test_embedded_audio_and_video_are_skipped_and_only_counted`）。Mac 发出的文件副本里，音视频本来就已清空。
- 一条素材的新修订在旧修订读之前就到了，旧修订的字节当场删除，永远不会被读（`test_bytes_of_a_revision_superseded_before_it_was_read_are_deleted`）。
- 文件里的图片（扫描页、Word 里的截图、改了后缀的图片或图片压缩包），只有 Mac 标明「这份副本里的图片都已涂过」时，Spark 才交给读图模型；否则跳过，只记一句「N 张图片未读取（未经 Mac 遮盖）」（`test_a_file_item_never_sends_an_unredacted_image_to_the_vision_model`）。
- 手机收件箱：Mac 取走并确认后，封好的条目立刻删除，文件里的旧内容会被覆盖（`test_sealed_add_list_ack`）。

### 5. 收回

- **删一条**：Mac 上删掉一条已经送达的素材，Spark 上它的所有修订、读图读文件的结果、向量、拆出来的片段、人物关联都会删掉；删一段录音，从它截出的关键帧也一起删。它**待过的每个事件**（现在所在的、之前被移出的、已被合并或被你删掉的）都立即清掉可能引用它的内容：现在的事件只留你自己改过的标题（或事件的锚点），状态行、排序理由清空，等重新整理；只剩它或已删除的事件整张卡片清空；它当初定下的锚点也清掉。读过它的模型调用（按记录的「读过哪些素材」，不靠文字前缀比对）和相关提问都清空，删除时正在进行的简报和排序结果直接丢弃，只留一个不含内容的墓碑。定期整理事件和人物整理的记录也一样：它们的每次模型调用都记下自己读了哪些素材，删掉其中任何一条，这次调用的输入、输出和提案都清空；这条素材的人物扫描记录（`person_scan`）删掉，因为它只剩下没有素材的人物记录的判断（`person_checks`）删掉，它待过的事件的整理记录（`consolidate_checks`，只有编号、条数和结论）删掉，那些事件下一轮重新判断；删掉的素材不会再被人物整理重读或搜索（`test_deleting_an_item_a_consolidation_call_read_clears_that_run_and_its_proposal`、`test_deleting_an_item_a_person_resolve_call_read_clears_the_run_and_the_record_of_the_pass`）。线索图（v7）也一样，图上不留任何从它写出来的字：凡是以它为出处的结都去掉（哪怕还有别的出处，和事件卡片上的事实一样），列过它的线整条去掉（线名和概要都可能是转述它），这条线上剩下的结回到主线；引过它的健康理由清空；引它原话的牵制关系删掉；这件事重新排队画图，重画失败就把图整张删掉，不保留旧图。事件被删掉、被合并或删到一条不剩时，它的图和排队记录一起删除。模型提议、你还没确认的绳如果以它为出处，整根绳连同名字删掉，里面的事以后重新判断；你确认过或改过名的绳保留你的决定，只去掉出处和理由（`test_deleting_an_item_prunes_maps_blocks_and_their_runs`、`test_every_knot_that_cites_the_deleted_item_goes_even_with_other_evidence`、`test_deleting_a_sample_item_drops_the_proposed_rope_written_from_it_and_clears_the_run`、`spark/tests/test_map_review_v7.py`）。交叉关系是现算的，不存；成股整理的判断记录只有事件编号、标题的哈希和结论。之后再有人送同一个 ID，回答 410（`test_delete_purges_every_revision_child_and_derived_row`、`test_delete_does_not_rely_on_a_successful_rebrief`、`test_delete_while_a_brief_is_being_written_leaves_no_copy`、`test_deleting_a_recording_also_deletes_its_keyframes`：删除之后，即使拿着钥匙把整个库读一遍，也找不到那条素材里的哨兵文字）。
- **正在送的也能收回**：关链路时还没确认送达的素材，Mac 会记下「可能已在 Spark 上」（不含内容）；之后删掉它，删除照样会发。
- **原文不许改**：模型输出和整理代码都改不了素材原文。数据库触发器只放行两种变动：你的删除，和读完就删；其他任何改写都会被拒绝（`test_item_content_is_never_rewritten_only_purged`、`test_item_blobs_are_never_rewritten`）。
- **全部忘掉**：清空要带上钥匙编号，编号对得上才执行，锁着的时候也能做。数据库（连同线索图、关系和绳）、WAL、钥匙编号文件、收件箱里还没取走的内容会全部删除，数据目录里的日志、服务自己的日志文件也会清空（`test_wipe_needs_the_matching_key_id_and_forgets_everything`、`test_wipe_empties_the_configured_log_file_and_the_process_log`）。清空那一刻还在跑的模型调用，结果不会写进之后新建的库（`test_a_model_call_in_flight_during_wipe_writes_nothing_into_the_next_store`）。Mac 这边如果钥匙串删不掉旧钥匙，会改写成一把新钥匙；两样都做不到，链路就停下，旧钥匙不会再用。
- **日志只记类型**：日志和健康检查里的错误只写错误类型（和 HTTP 状态码），不写错误正文；锁着时健康检查不显示任何错误。

### 6. 功能不打折

口述、录音、识别、插入、搜索都在 Mac 上完成，不依赖 Spark。链路关着时，事件页由 Mac 在本机整理；Spark 回来后，积压的删除最先送，然后是你的修改，再然后是新素材。

|---|---|---|
| 原来（明文，带图片和文件字节） | 98,037,760 | 64,925,669 |
| 读完就删之后（明文） | 89,329,664 | |

## 手机

手机上的入口是 iPhone App「织机」：织机键盘（按住说话，文字直接进当前 App）和分享扩展「收进织机」。搭建和接口见 [PHONE.md](PHONE.md)。第 1、2、5 条和封存本身在 iPhone App 里做到，测试在 Mac 客户端仓库（`Packages/MindloomLink`、`Packages/MindloomPhoneKit`、`iOS/`）；第 3、4 条的 Spark 一半在本仓库。五条保证：

1. **和现在一样省事。** 在手机上切到织机键盘，按住麦克风键说话，文字就出现在微信、邮件或任何 App 里；地球键回到平常的键盘。不用养成新习惯。
2. **声音不离开手机。** 识别在手机本机做（Apple 的离线语音识别，中文）。声音只在内存里留到这一句识别完，从不写盘、从不发出。只在 Mac 上的词典和声纹从不到手机上。
3. **在手机上锁好，只有你的 Mac 能打开。** 每一条离开手机之前，都封给你 Mac 的公钥（X25519 + HKDF-SHA256 + ChaCha20-Poly1305，条目 id 也在认证范围里）。Spark 只转交封好的字符串，没有能打开它的钥匙；它只检查样子（前缀、字符、长度），原样保存，条目 id 一个字节都不改。Mac 取走后，Spark 删掉它（`test_sealed_add_list_ack`、`test_what_the_mac_gets_back_opens_with_the_id_it_was_sealed_under`、`test_sealed_entries_refuse_anything_but_the_contract_shape`）。
4. **一把只能做一件事的钥匙。** 手机的 SSH 密钥在 Spark 上被锁在 `zhiji-inbox gate` 上：只能放进来（`add`）和问还有几条（`status`），配对命令、文件路径、shell 都被拒绝，也不能转发端口。经跳板机时，它在跳板机上只能开一条到 Spark SSH 端口的隧道：不能执行命令，不能连别的地址，不能开监听端口。手机丢了，这把钥匙最多往收件箱里塞封好的条目。在 Mac 上「断开 iPhone」会删掉 Spark 和跳板机上的这两行，之后这把钥匙哪儿都进不来。这些都用真的 OpenSSH sshd 验证过（`test_sshd_holds_the_phone_key_to_the_gate`、`test_sshd_holds_the_phone_key_on_the_relay_to_one_tunnel`），写 `authorized_keys` 时其他行一个字节都不动（`test_authorize_appends_one_restricted_line_and_leaves_every_other_line`、`test_revoke_removes_only_that_phone_and_is_idempotent`、`test_relay_helper_adds_replaces_removes_and_lists`）。
5. **音视频不从手机分享。** 分享扩展看到音频或视频会说「音视频请在 Mac 上导入」。其他都收：文字、链接（从不打开）、图片（在手机上重新编码，去掉拍摄地点等元数据）、文档（≤ 25 MiB）。

另外要知道的：

- Spark 看得到的只有条目 id（随机 UUID）、收到的时间和封好之后的大小；看不到是什么、来自哪个 App、写了什么。
- 键盘开着语音的时候，系统的麦克风指示会一直亮着（最后一次用完 10 分钟后关）；只有按住麦克风键时说的话才会被识别，其余的声音在进来的那一刻就丢掉。键盘看不到你用别的键盘打的字。
- 手机上送达的条目只留 7 天的文字预览（图片不留），方便你看到「已送出」。
- 以前的 iOS 快捷指令「分享到织机」已经停用：它没法封存，内容在 Spark 收件箱里等 Mac 取走时是明文。现在 Spark 只收封好的条目：手机密钥的 `gate` 只放行 `add --sealed --id <UUID>` 和 `status`，明文的 `add` 回答 `not_sealed`，接口对明文条目回答 422 且不回显内容（`test_plaintext_adds_are_refused_and_nothing_is_sent`、`test_inbox_refuses_plaintext_and_bad_input`）。

## 共享空间

共享空间用的是同一套规则：Spark 只看到整理需要的东西（遮过号码的文字、缩小的图，只在某位成员的 Mac 借出钥匙时、只在内存里）；人看到的是你给的（原件端到端加密给成员，Spark 存密文、打不开）；声纹、词典、个性化识别从不进任何空间，录音只按片段共享。空间里的线索图和绳也是整理结果，同样只在空间的加密整理库里，成员撤回或移除素材时按上面「删一条」的规则清掉。怎么做到、边界在哪，见 [SPACES.md](SPACES.md)。

## Agent 读取织机（Mac 端）

Claude Code 这类 Agent 读的是 Mac 上的织机，经 App 自带的本机连接程序和一个只有你能用的本机通道；Spark 不参与，也不经过 Spark。每个 Agent 第一次读之前要你同意，范围、期限、号码遮挡由你定（默认遮号，规则和发给 Spark 的相同）；音频、声纹、词典永远不给。Agent 背后的模型通常在它厂商的云上，所以它读到的文字会离开 Mac——同意窗口写明这一点。共享空间里的事单独标着空间，只给授权了那个空间的 Agent；读到时，那个空间的操作日志多一条不含内容的 `agent.access`。详见 Mac 仓库的 `docs/AGENTS.md`。

## 链路本身

- 整理服务只在权限 0700 的数据目录里的 Unix socket 上监听，默认不开 TCP。每个请求都要链路令牌，令牌检查排在上锁检查前面，没有令牌的人连「锁没锁」都问不出来。
- Mac 用你自己的 SSH 密钥连过去，每个请求前都核对本机转发端口确实是 App 自己启动的 ssh 在监听。令牌另走一条 SSH 读进内存，不写盘、不进日志。
- App 里没有内置主机，你不填就不连任何机器。只有带合成数据标记的资料库能打开链路。

## 威胁和防护

| 担心的事 | 防护 |
|---|---|
| 同一台 Spark 上的其他人 | 数据目录 0700；库是密文，钥匙不在磁盘上；开锁期间只拿令牌读不到（要钥匙推出的访问凭证）；Mac 不在超过 10 分钟就自己锁上；进程不可转储 |
| Spark 的硬盘被拷走，或服务被重启 | 磁盘上只有密文和钥匙编号；重启后在 Mac 连上之前什么都读不出 |
| 录音、声纹被送出 Mac | 发送类型里没有这些字段；Mac 的哨兵测试逐字段比对报文 |
| 号码、密码、验证码出现在文字或截图里 | 出门前遮住或涂掉；Spark 再遮一遍；共享测试向量保证两边一致 |
| 图片和文件在 Spark 上越攒越多 | 读完即删，Spark 上的图片和文件字节恒为 0 |
| 想收回一条 | 删除同步到 Spark，删得彻底，之后再送同一 ID 回答 410 |
| 想让 Spark 全部忘掉 | 一键清空，并销毁 Mac 上的钥匙 |
| 用错钥匙，或别人的 Mac 来开锁 | 409，库保持锁着 |
| 素材里藏着指令 | 素材只当数据；动作只能由代码从模型的判断推出，或由你在界面上发出 |
| 恶意文件 | 在断网、限时、限内存的子进程里解析；压缩包炸弹不展开；音视频不解码 |
| 手机丢了，或手机的 SSH 密钥泄露 | 那把密钥在 Spark 上只能往收件箱里放封好的条目、问条数；在跳板机上只能开一条到 Spark SSH 端口的隧道。读不到任何数据；在 Mac 上断开 iPhone 就吊销 |
| Spark 读手机送来的内容 | 在手机上就封给了 Mac 的公钥，Spark 没有私钥；条目 id 在认证范围里，Spark 改不了 |
| 有人冒充 Spark 或跳板机 | 手机只认配对时固定下来的主机密钥，对不上就在握手阶段断开，手机的钥匙都不会拿出来 |

## 诚实的边界

1. **开着锁的时候，明文在进程内存里；共用账户挡不住有心人。** 整理要读文字，所以开锁期间，遮过号码的文字以明文形式在整理进程的内存里；这台 Spark 的 root 能读。进程设成了不可转储，同一账户下的普通程序读不了它的内存，只拿令牌也读不到库；但能以同一账户运行程序的人，可以停掉整理服务、自己占住那个 socket，等你的 Mac 下次连上时骗到钥匙（Mac 没法证明对面是真的整理服务）。所以：**请用一个只有你自己用的账户跑整理服务**，别和团队里的其他程序、其他人共用一个登录账户。上锁会关掉数据库、丢掉钥匙，但 Python 抹不干净内存里残留的副本，只能尽力。
2. **同一台 Spark 上的模型服务看得到提示词。** 提示词是遮过号码的文字，但仍然是你的内容。模型服务由部署者自己启动，本仓库不启动它，也证明不了它不记请求日志、有没有关掉 vLLM 的使用统计。我们自己启动的向量服务显式设置了 `VLLM_NO_USAGE_STATS=1`、`DO_NOT_TRACK=1`、`HF_HUB_OFFLINE=1`。
3. **删掉的文件，磁盘块可能还在。** 旧的明文库在第一次开锁时被加密并删除；删一条素材时，库内被释放的页面会被覆盖。但文件系统和 SSD 可能还留着旧的磁盘块，要彻底抹掉，只能靠整盘加密或物理销毁。
4. **手机收件箱只存密文。** 锁着的时候也要能收手机的东西，所以收件箱是一个单独的小库，不加密；但 iPhone App 送来的每一条都在手机上封好了，Spark 打不开，只原样保存，Mac 取走即删、覆盖；清空时还没取走的也会删掉。Spark 能看到每个条目什么时候到、有多大。以前不封存的备用入口（iOS 快捷指令）已经停用，手机的 SSH 密钥只能放进封好的条目。
5. **遮号码只认规范里的号码。** 规范第 2 版（复查之后）补上了先写号码再写「验证码」、全角数字、口述的中文数字、被点号或换行拆开的号码、带括号或空格的座机、国外号码、美国运通卡、账号后面的公司账户、写成分组或 15 位的身份证号、更多密钥格式；第 3 版（遮号评测之后）补上了聊天里后说出来的验证码（共享向量 200 条）。仍然认不出的：隔了一句话或 40 个字以后才说出来的验证码，没有任何提示词、也不是手机号格式的 8 位号码，手写的号码，拆成三行以上的号码。反过来，一句提到验证码的话里，「是」「为」或冒号后面的 4–8 位数字（比如房间号）也会被遮住：拿不准时宁可遮。人名、日期、金额、地点、地址本来就不遮。
6. **占位符挡模型、挡日志，挡不住拿着钥匙的人。** 占位符由一把从资料库钥匙推出的遮号钥匙算出，开锁期间这把钥匙在 Spark 进程里。像 6 位验证码这样的短号码，有这把钥匙的人一个个试就能试出来（约 100 万次）。遮号码防的是号码进提示词、进模型服务、进日志，不是防拿到钥匙的人；拿到钥匙的人本来就能解开整个库。
7. **截图涂抹靠这台 Mac 自己认字。** 竖排文字、手写、艺术字、极小的字，Mac 认不出也就涂不掉。复查后加了放大分块再认、跨表格和换行拼读、「连续 7 位以上数字就涂」三道补救，复查用的 13 种合成截图现在都涂干净了，但不能保证所有排版都认得出。
8. **少数文件格式原样发送。** 老式二进制 Office 文件（.doc、.xls、.ppt）和邮件文件（.eml）里可能嵌有图片或录音，Mac 不拆开它们；Spark 不读其中的图片、不解码其中的音视频，但字节会经过链路，读完即删。
9. **删除以素材为单位。** 只在被删素材里出现过的人名记录会留到清空为止（它的人物整理判断会删掉）。事件卡片里其他素材的事实会保留，标题和状态行在重新整理后更新。
10. **有几个环节还没有实证。** 真实资料库还没打通（发布开关关着），Spark 整理只在合成资料库上跑过。iPhone App 只在 iOS 模拟器上测过，没在真 iPhone 上跑过；模拟器里没有中文离线识别模型，真机上的识别效果还没验证。
11. **手机丢了以后，钥匙在吊销之前还能用。** 在 Mac 上断开 iPhone 之前，捡到手机的人如果能解锁它，可以往收件箱里塞封好的条目（Mac 会照常取走），但读不到任何东西。

## 实测：端到端和 Spark 实际收到了什么

- **隐私端到端（整合版，68/68）**：Mac 端是真实代码（资料库、链路、SSH 转发、截图涂抹），Spark 端是一个真实的 v6 整理服务实例。五条合成素材（口述、粘贴文字、PDF、聊天截图、xlsx），每条带 7 种哨兵号码：线路上的每个请求里都没有哨兵；只拿令牌、不带访问凭证读，回答 403；Spark 上 9,554 个文件逐字节扫描 0 处命中，用钥匙解密逐行扫描也 0 处；删除、上锁、断开时删除、「忘掉我」、锁着时清空都按上面说的生效。
- **手机端到端（整合版，67/67）**：iOS 模拟器里的 App 经跳板机把 3 条封好的条目送进真实 Spark 的收件箱；Spark 上 9,552 个文件扫描 0 处明文；Mac 取走后照常遮号、整理；「断开 iPhone」之后手机再发被拒，两台主机的 `authorized_keys` 和开始时逐字节相同。
- 数字和前几次没全过的原因见 [EVALUATION.md §11.4、§12](EVALUATION.md#114-mac--spark-隐私端到端) 和 `eval/results-2026-09-30/integration.json`。
- **v7 整合后重跑（2026-10-01）**：在一个全新的 v7 整合版实例上依次重跑，全部通过：隐私端到端 68/68（9,638 个文件逐字节扫描 0 处明文）、手机端到端 67/67（9,644 个文件 0 处明文；两台主机的 `authorized_keys` 和开始时逐字节相同）、共享空间端到端 57/57（两个合成资料库共享实验室的同一件事；Spark 的数据和日志目录里，哨兵号码、词典、声纹、窗口标题、空间名、成员名和实验室用词都是 0 处）。

**截止时的出网统计**：三个规模场景（合成数据）结束后，只读打开 Spark 上的整理库，逐条统计 Mac 发来的内容：每个场景 7.6–12.6 MB，只有文字、文档文字和截图；音视频文件头 0 个，长度 ≥32 的浮点向量 0 个，162 张截图的 EXIF 里只剩像素尺寸和色彩空间。这批素材本来就没有音频，所以这组数字不能证明「不发音频」（那由发送类型和测试保证），它说明的是出网内容可以这样逐字节核对。数字和脚本见 [EVALUATION-2026-09-29.md](EVALUATION-2026-09-29.md#12-隐私spark-实际收到了什么) 和 [eval/results-2026-09-29/](../eval/results-2026-09-29/README.md)。这组测量早于「遮号码」和「读完就删」。

## 仓库里有什么、没有什么

- 仓库里的评测和演示数据全部是虚构的合成数据；截图是通用聊天界面样式的合成图。评测和测试用的整理库用一把公开的合成钥匙加密（`spark/organizer/keys.py`），真实资料库从不使用它。
- 仓库不含模型权重、音频、真人口述、个人整理模型或评测用的私人资料。依赖私人资料的评测脚本没有公开。
- 日志不记录音频、完整逐字稿、词典内容、声纹或参与者信息；整理服务只记编号和计数，关闭了访问日志和接口文档页。
- **已知的出站请求**：安装模型时从 Hugging Face 按固定 revision 下载。Mac App 的自动更新检查默认关闭；打开后只请求本仓库 GitHub Releases 的公开元数据，不带 cookie 和用户内容。Mac 端没有分析或崩溃上报 SDK。
- 「复制这件事」「导出为文本」只在你点击时发生；织机没有和任何云端助手的 API 集成，内容进不进云端由你决定。

## 接口（给工程师）

整理服务的接口都要链路令牌。锁着时，除下表标注「锁着也能用」的以外，其他数据接口都回答 `423 {"error":"locked"}`。Mac 开锁之后，数据接口还要 `X-Mindloom-Access: HMAC-SHA256(钥匙, "mindloom-access-v1") 的十六进制`，不对回答 `403 {"error":"access"}`（公开的合成钥匙除外）；超过 `ORGANIZER_UNLOCK_LEASE_S`（默认 600 秒）没有数据请求，服务自己上锁。文件素材可带 `pictures_redacted: true`，表示 Mac 已涂过其中所有图片。

| 接口 | 作用 |
|---|---|
| `GET /v1/health` | 多了 `locked` 和 `key_id`（磁盘上那个库的钥匙编号，没有库时为 null）。锁着也能用 |
| `POST /v1/unlock {"key": 64 位十六进制}` | 开锁或新建加密库：200 `{"locked":false,"key_id","created"}`；钥匙不对 409 `{"error":"wrong_key","key_id"}`；格式不对 400。同一把钥匙重复开锁不出错 |
| `POST /v1/lock` | 关库、丢钥匙、暂停整理：200 `{"locked":true}`。锁着也能用 |
| `POST /v1/wipe {"key_id"}` | 编号对得上，或者还没有库，就删除整理库、WAL、钥匙编号文件、收件箱里未取走的内容，并清空数据目录里的日志：200 `{"wiped":true}`；编号不对 409。锁着也能用 |
| `DELETE /v1/items/{item_id}` | 删除一条素材的全部修订和派生内容，留一个不含内容的墓碑：200 `{"deleted":true}`，未知 ID 也是 200。之后 `POST /v1/items` 送同一 ID 回答 410 `{"error":"deleted"}` |
| `GET /v1/stats` | `{"items","blob_bytes","db_bytes","derived_bytes"}` |
| `POST /v1/inbox` | 手机的条目放进来。锁着也能用（单独的 `inbox.db`）。只收封好的条目 `{"inbox_id":小写 UUID,"source":"sealed","kind":"sealed","blob":"mlseal1.…"}`，只检查样子、原样保存；回答 `{"ok":true,"id","inbox_id","duplicate"}`。明文条目（`kind` 为 `text` / `image`）和样子不对的一律 422，不回显内容 |
| `GET /v1/inbox`、`POST /v1/inbox/{id}/ack` | Mac 取走和确认；封存条目是 `{"inbox_id","kind":"sealed","blob","received_at","seq"}`，确认后删掉 `blob` |

## 复查之后（2026-09-30）

对抗式复查查出 16 个问题（3 高、7 中、6 低）。改法和对应的测试：

| 问题 | 改法 |
|---|---|
| 开锁后一直开着；同一账户的人拿令牌就能读 | 访问凭证、10 分钟租约、Mac 睡眠和退出时上锁并重试、进程不可转储；共用账户的风险写进上面的边界 |
| 截图涂抹漏掉长截图、方格里的数字、表格单元格、竖排、没对齐的换行、点号分隔、号码在前的验证码 | 放大分块再认，按行、按列、按阅读顺序拼读，连续 7 位以上数字就涂，形近分隔符归一；13 种合成截图全部涂干净，Spark 的读图模型也读不出 |
| 文件字节里的图片和录音原样过链路 | Mac 重做发送副本（图片涂掉、音视频和嵌入对象清空、扫描页重绘后涂掉）；改了后缀的图片按图片收；Spark 只读 Mac 标明已涂过的图片 |
| 「忘掉我」与正在跑的模型调用赛跑 | 每一步绑定开锁会话，会话变了就什么都不写 |
| 删除漏掉副本 | 见上面「删一条」 |
| 删录音留下关键帧 | Mac 和 Spark 都连带删除 |
| 被新修订替换的旧字节不删 | 当场删除，旧库打开时补删 |
| 30 种常见号码格式没遮 | 遮号规范第 2 版 |
| 手机收件箱是明文 | iPhone App 在手机上封好再送，Spark 只收封好的条目；不封存的旧入口已停用 |
| 崩溃转储可能带钥匙 | 不可转储、核心转储上限 0 |
| 钥匙串删不掉时继续用旧钥匙 | 改写新钥匙，做不到就停 |
| 来源名没有再遮一遍 | 再遮，删除时清空 |
| 短占位符可被试出 | 写进边界，未改 |
| 发送途中关链路的素材删不掉 | 记下「可能已在 Spark 上」 |
| 清空不清服务日志，锁着时暴露错误正文 | 清服务日志和进程日志，只记错误类型 |
| 太大的文件带着原文件的校验值 | 改为发出文字的校验值 |

## 整合之后（2026-09-30）

隐私、手机和整理质量三条分支合到一起时，补上了它们之间的缝：

| 缝 | 做法 |
|---|---|
| 手机收件箱还留着快捷指令的明文入口 | 只收封好的条目，明文的 `add` 和接口条目一律拒收 |
| 新加的定期整理事件、人物整理可能在上锁或「忘掉我」之后写进新库 | 和整理素材一样绑定开锁会话，并发的模型调用也一样 |
| 删一条素材时，这两个整理环节的记录还留着它 | 调用记下读过的素材；人物扫描记录、只剩下被删素材的人物判断、它待过的事件的整理记录一起删 |
| 两个新 Skill 的说明缺占位符和「素材即数据」 | 补上（event-consolidate 1.0.1、person-resolve 1.2.1） |
| 遮号评测漏掉的验证码说法 | 规范第 3 版，共享向量 200 条 |
| 遮号评测里模型改坏的占位符 | 每个 Skill 的输出先修补再校验、存盘 |

## 整合之后（2026-10-01，v7）

线索图、共享空间和 Agent 读取三条分支合到一起时补上的缝：

| 缝 | 做法 |
|---|---|
| 共享空间的整理器也会画线索图、搓绳，撤回的素材可能留在图里 | 空间用同一个整理器和同一套删除规则；有测试证明撤回后图里不留它（`spark/tests/test_v7_integration.py`） |
