# file-read benchmark

## file-read 1.0.0 · files-v1（代码 679f580，2026-09-29）

测的是整理器里真实的那条路径（`organizer.file_read.read_file`）：沙箱子进程解析 → 图片部分走 image-read（同一套技能、harness、引导解码、校验和重试）→ file-read 写概要和关键字段（校验器、重试一次、仍不合格时清理）。

- **数据**：`eval/files` 的 files-v1 合成文件集，20 个模板 × 3 个变体 = 60 个文件（全部虚构）。每个模板的变体 a 是 dev（20 个），b、c 是 test（40 个）。
  类型覆盖：docx（含嵌入图片）、LibreOffice 生成的 .doc / .xls / .ppt / .odt / .rtf / PDF、xlsx、csv（GB18030）、pptx（含图片和备注）、扫描 PDF（两页 mm-v1 扫描件）、eml（xlsx 和照片附件）、ics、vcf、webarchive、zip（docx + csv + 白板照片）、md、epub、Keynote 预览、加密 PDF。
  图片部分用 mm-v1 **同一划分**的图（dev 文件用 dev 图，test 文件用 test 图），它们的金标准来自 `eval/multimodal/gt`。
- **只在 dev 上调**：dev-r1 之后改了三处（合同双方可以是两个 `parties` 字段；起止日期分成两个字段；扫描页标签缩短），dev-r2 之后修了扫描件和图片部分的金标准写法；然后冻结代码 679f580 跑 test。
  dev-r3 之后、看 test 结果之前，又把 4 个模板（keynote、roadmap、training、notes）的概要关键词从"标题前几个字"改成主题词，并用 `run_files.py --rescore` 对已保存的 test 记录重新计分；重算前后 test 的概要命中完全相同（见 `results/*/summary.json` 与 `summary_rescored.json`）。
- **模型**：Qwen3.6-35B-A3B NVFP4，vLLM 0.30.0，spark-C `127.0.0.1:8000`（`~/hack/claude-files/serve_qwen36.sh`，与 spark-B 相同的参数：MTP×3、`--gpu-memory-utilization 0.55`、8 路），thinking 关，temperature 0。
  **这个服务和另一个工作流共用**，所以下面的时延是上限，不是独占数字。
- **并发**：两个文件同时跑，一个文件内的图片部分最多 4 路并发。
- **条件**：有技能 = 发布的 SKILL.md；无技能正文 = `eval_common.strip_skill_text`（**所有**技能的正文换成一行任务名，所以图片部分的 image-read 也没有技能正文；全局规则、schema 引导解码、校验器、重试都保留）。
  提示哈希：有技能 `5810c0096d0a5445`，无技能正文 `f8cbae666459776e`。
- **计分**：`eval/files/run_files.py`。比较前做 NFKC、去空白、全半角标点视为相同。
  - 类型：读取结果的 `type` 和 `error` 都对。
  - 文字召回：金标准里只靠解析就能读出的句子（标题、表格行、邮件头……）在读取文字里出现的比例。
  - 图片召回：只有 image-read 读对了才会出现的字（图片第一行和一个带数字的印刷词）。
  - 概要命中：每个文件 1–2 组主题词，一组里任一个词出现在概要里算命中。
  - 模型概要：有文字的文件里，概要来自模型（第一次或重试后合格），而不是清理后的或整理器自己写的。
  - 关键字段：票据、订单、合同的金标准字段值出现在读取结果的某个字段值里（test 共 6 个文件）。代码字段：邮件头 / 日程 / 名片 / 电子书由代码读出的字段完全一致。

### 只解析（不调模型，60 个文件）

类型 60/60，文字召回 100%（51 个有文字金标准的文件），p50 0.07 s / p90 0.13 s（`results/all-parse`）。LibreOffice 生成的真实 .doc / .xls / .ppt 都由自带的解析器读出。

### test（40 个文件，每个条件两次）

| 条件 · 运行 | 类型 | 文字召回 | 图片召回 | 概要命中 | 模型概要 | 首次合规 | 关键字段 | 代码字段 | p50 / p90（整份） | 无图 p50 / 有图 p50 |
|---|---|---|---|---|---|---|---|---|---|---|
| **有技能 · r1** | 40/40 | 100% | 100%（12） | 98.8% | 38/38 | 36/38 | 100%（6） | 100%（6） | 7.4 / 25.0 s | 5.7 / 23.6 s |
| **有技能 · r2** | 40/40 | 100% | 100%（12） | 95.0% | 38/38 | 36/38 | 100%（6） | 100%（6） | 7.8 / 33.1 s | 5.9 / 27.0 s |
| 无技能正文 · r1 | 40/40 | 100% | 93.8%（12） | 93.8% | 33/38 | 1/38 | 100%（6） | 100%（6） | 18.3 / 50.2 s | 12.8 / 46.4 s |
| 无技能正文 · r2 | 40/40 | 100% | 91.7%（12） | 95.0% | 33/38 | 2/38 | 100%（6） | 100%（6） | 14.2 / 49.9 s | 11.6 / 40.2 s |

- 两个加密 PDF 两次都报 `error: "encrypted"`，概要是整理器自己写的，不调模型（所以"模型概要"的分母是 38）。
- **没有技能正文时**，file-read 的第一次输出几乎都被校验器拒绝（38 次里只有 1–2 次一次过；本次没有保存第一次的拒绝原因），重试后仍有 5 个只能清理，时延因此翻倍；image-read 失去技能正文后扫描页漏读（图片召回 92–94%）。
- **有技能时**没过的概要命中都是金标准的主题词太窄：概要写"开票日期…金额 3,460.50 元"而没写"发票"两个字（invoice-b），写"Q3 营收 186.4 万元"而没写"复盘"（keynote-c）；扫描件 scan-b 两页是两份不同的文档，概要把两份都说了，但没写"点单小程序"这个词。概要里的数字都能在文字里找到（校验器保证）。
- 有图片部分的文件慢得多：每张扫描页 / 嵌入图片是一次两步的 image-read（约 4–10 s），再加一次概要。

### 复现

在 Spark 上、仓库根目录（需要 LibreOffice 生成数据，整理器 venv 另加 pypdf、xlwt）：

```bash
python eval/files/generate.py                                   # 生成 data/、gold/、manifest.json
python eval/files/run_files.py --split all --parse-only --out /tmp/files-parse
python eval/files/run_files.py --split test --out /tmp/files-test-r1 --workers 2 --llm-url http://127.0.0.1:8000/v1
python eval/files/run_files.py --split test --condition bare --out /tmp/files-bare-r1 --workers 2
```

生成器每次的字节不完全相同（LibreOffice 和 zip 写入时间戳），内容相同；已提交的 `eval/files/data` 是这次评测用的那一份（`manifest.json` 里有每个文件的 sha256）。

### 局限

- 合成文件比真实文件干净：排版规整、没有页眉页脚噪声、表格不跨页；真实的 .msg 没有样本（只有流的替身测试）。
- 每个条件 n = 2；vLLM 在 temperature 0 下也不完全可复现；服务是共用的，时延只能当上限看。
- 概要命中只看主题词，不评判概要写得好不好；关键字段的 test 金标准只有 6 个文件。
