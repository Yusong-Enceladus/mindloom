# item-split benchmark

## 当前代码是 1.3.1（1.3.0 加一句占位符说明，没有重新评测）：参照用户自己的事来切（2026-09-30）

1.3.1 只比 1.3.0 多一句「占位符（如〔手机号·a1b2c3〕）是被遮住的号码，原样保留，不要猜、不要改写。」下面的数字都是 1.3.0 的。整理器现在还会在校验之前修好输出里被写坏的占位符（遮号评测里 item-split 把〔验证码·3feb18〕写成过「邮箱验证码3feb18」），修补只动这次输入里出现过的占位符。

**问题**：规模数据上，1.2.0 仍把只讲一件事的素材切开 30.6%（lab）/ 19.7%（pm）。被切开的大多是同一个项目的几个方面
（前端、模型、测试、分工、排期被当成几件事），或者一条主要讲一件事的素材里顺带提了一句另一个项目。

**改动**（`SKILL.md` 1.3.0、`scripts/units.py`、`scripts/validate.py`、`organizer.decide_split`）：

1. 整理器把用户当前最大的 24 件事（至少 3 条素材的事件，按大小取、按创建顺序列出标题）作为 `known_matters` 一起给模型；
   模型按"是不是这里的同一行"来判断几块是不是一件事，并为每件事写出它属于哪一行（`known`）。写了同一行的几件由程序合成一件（`units.joined_matters`）。
2. 一件事要算"实质"，除了原来的"≥ 2 个单元或 ≥ 12 个字"，还要占这条素材里有事部分的 ≥ 15%，或者自己就有 ≥ 150 个字（顺带一提不算）。
3. 两次都不合格的输出，如果只是有一件事没有段、段的顺序乱了或重叠、`known` 写了没给过的编号、gist 太长，程序直接修好再用（`units.salvage`），不再因此整条不切。

**怎么测**（`eval/tools/split_scale.py`，只切不归）：对三个规模场景，取整理器当时实际收到的素材（`fixture`），按整理器的同一段代码
（`Organizer.decide_split`：会议解析、单元、预筛、技能、校验、修补、`segments_from_output`）重新切一遍，用 2026-09-29 规模报告的同一套分段真值口径打分。
`known_matters` 取整理完（含事件整理）的最终状态里、在这条素材之前已有 ≥ 3 条的事件和它们的最终标题——对早期素材偏乐观；真实效果看留出场景的完整运行。
lab、pm 是调参集，startup 是留出集，只在最后跑一次。模型 Qwen3.6-35B-A3B NVFP4，关闭思考，temperature 0，同一节点上还有别的负载。

少切以后归事件和简介的调用也少了（assign 3,005 → 2,572、brief 2,955 → 2,582），所以虽然每次切分的输入多了约 1,200 token，
整体输入 token 反而少了 3.1 M。易干扰泄漏的"易"那一项变差（一对易混事件被合进了一件，每个场景只有几对）。每个条件只跑了一次。

- "顺带一提不切"的阈值（15% / 150 字）是在 lab、pm 的 1.3.0 输出上离线扫出来的（10% / 15% / 20% × 不设 / 150 / 300 字）：15% / 150 字在两个 dev 场景上
  都让切开率再降 2–4 个点，每件事被找回只降 0.005 左右；20% 降得更多，但召回掉 0.03–0.05。
- 代价：多件事的素材里每件事被找回 lab 0.701 → 0.695、pm 0.829 → 0.808，"全部找回" lab 0.571 → 0.537、pm 0.645 → 0.607。
- 剩下被切开的"单件事"素材，多数是模型把几块分到了 `known_matters` 里**不同**的行：一条口述里连着说了几个项目，场景真值只记了其中一件。
  这部分和真值的定义有关（场景生成时每条素材只规划了一个主事件），不全是错切。
- 调用：每次切分的输入多了约 24 行事件标题。
- 技能用例（`eval/run_skill_evals.py --skills item-split --n 3`，最终代码）：10 个虚构用例（新增 2 个带 `known_matters` 的：同一件事的三块不切、
  两件已知的事切成两段）3 次全过（1.000）；之前 1 次没过的提示词注入用例 split-005 这次 3/3。

- 端到端的差别在 n = 1 的波动范围内（dev 上最终版两次之间就差 0.03）：split-dev 的 B³ F1 0.654 → 0.686、难干扰泄漏 0.167 → 0.262；

- dev 上两个版本都只切开了同一条素材：同一个项目的两件子任务（技能说这种情况不该切）。两段都归进同一事件，对分数没有影响；Mac 上显示为同一事件里的两段。
- split-dev 的主要损失在召回：预测事件 21 个对真实 11 个，说明切出来的段常常新建事件而没归进已有的同一件事。
