# event-consolidate benchmark

当前代码是 **1.0.1**：只比 1.0.0 多一句占位符说明（「占位符（如〔手机号·a1b2c3〕）是被遮住的号码，原样保留，不要猜、不要改写。」），没有重新评测；下面的数字都是 1.0.0 的。整合进隐私版本（2026-09-30）以后，整理环节只在库开着锁时运行，模型调用绑定开锁会话，每次调用记下读过的素材（删除素材时据此清掉记录），输出先修补被写坏的占位符；这些都不改变判断本身。

## 1.0.0（2026-09-30）

**为什么要它。** 整理器一条一条地归素材。三个 1,500–1,600 条的合成规模场景跑完以后，事件数是真实事情数的 11–17 倍
（lab 242/22、pm 227/21、startup 348/20），只有一条素材的事件有 109–233 件；噪声（闲聊、群发通知、取件码）有 28–58%
自己成了一件事。一件真事常常只对上一个小碎片。提问解决不了这个问题：提问预算很小，补录的时候也没人回答。

**它做什么。** 整理器自己定期收拾（`spark/organizer/consolidate.py`）：每处理 25 条素材一轮；队列空闲时，攒够 5 条新素材、
空闲 5 分钟或上一轮刚改过东西时再跑一轮；每轮最多判断 40 个事件（另加合并前的二次确认）。确定性的部分在 `scripts/directory.py`：事件目录（最大的
32 个事件，整轮固定，同一轮的调用共享提示前缀）、要判断的事件（从小到大，≤ 120 条）、每个事件最像的几个事件（向量质心余弦）、
允许合并的对象和重判规则（翻倍、上次判断作废、或近邻里出现可能的归宿时才重判，最多 4 次）。模型对每个小事件写出最像的那件事、
两者关系（same / part / related / none）和结论：只有 same 才合并（保留较大的那个，另一个带 `merged_into` 删除）；≤ 9 条的
非事件放回未归档；其余保留。护栏：10 条以上的事件只和最像的 3 个比、看得到双方的素材；一边 ≥ 10 条或两边都 ≥ 3 条的合并
要只给这一对再确认一次；20 条以上的只和大小相近（≤ 4 倍）的合并；两个 ≥ 10 条的事件标题/对象要有两个共同词（不算用户
自己的名字）。用户改过名、置顶、亲手放过素材的事件不动，用户说过"不是同一件事"的两件不合并。

**数据与独立性。** 全部是合成数据。调参只用 dev：规模场景 lab、pm 的副本（离线工具，10 轮），以及 dev-week-v1。
startup（规模留出）只看过总数、从没用来调参；holdout-week-v2（小留出集）是历史头条用的集，这里用了两次（中间版本和最终版本
各 2 次），第一次的结果没有用来改设计（改设计的依据是 dev-week-v1 上同样的两种错）。技能自带的 12 个用例全部虚构。
模型：Qwen3.6-35B-A3B NVFP4（vLLM，关闭思考，temperature 0）；向量：Qwen3-Embedding-0.6B；每个场景一台 DGX Spark。

### 规模场景：运行时路径

每个场景的最终状态复制一份，起一个带整理环节的整理器实例（4 个 worker、回放时钟），**不发任何新素材**，它空闲时按运行时的
规则自己整理、重写被合并事件的卡片、重排首页，直到状态不再变化；再用和规模报告相同的评分器和 ID 对照打分。lab 做了两份：
一份从原始状态开始（和 pm、startup 同口径），一份从上一轮离线合并后的状态继续（184 件）。

| lab（从合并后的状态继续） | dev | 184 → **59**（22） | 99 → 21 | 0.706 → 0.682 | 0.620 → 0.744 | 0.660 → **0.712** | 0.662 → **0.744** | 0.610 / 0.276 / 0.114 → 0.762 / 0.095 / 0.143 | 0.227 / 0.093 → 0.334 / 0.111 |

| startup | **留出** | 348 → **84**（20） | 233 → 33 | 0.678 → 0.665 | 0.514 → 0.661 | 0.584 → **0.663** | 0.582 → **0.706** | 0.317 / 0.583 / 0.100 → 0.475 / 0.283 / 0.242 | 0.068 / 0.334 → 0.089 / 0.362 |

- 事件数：两个 dev 场景降到真值的 2.5–2.7 倍；留出的 startup 降到 4.2 倍（中间版本是 3.4 倍），没有达到 3 倍以内。
- B³ F1 在四份上都提高了 0.05–0.09，全部来自召回（碎片并回了它的事）；精确率持平或略降。
- 噪声：自成一件的比例在三个场景都下降（lab 0.28 → 0.07–0.10、pm 0.52 → 0.37、startup 0.58 → 0.28），但"混进真事"
  在 lab 和 startup 上升了（startup 0.10 → 0.24）：一部分噪声小事件被当成碎片并进了真事。
- 难干扰泄漏：lab 从 0.23 升到 0.33–0.34，主要是一场开放日演示被并进了它演示的那个实验（演示的标题里就有实验的名字，
  名字护栏拦不住）；pm 和 startup 略升。
- 卡片：被合并的事件会重写卡片。卡片事实召回 pm 0.652 → 0.870、startup 0.583 → 0.633、lab（原始）0.489 → 0.533，
  lab（继续）0.533 → 0.467。

目录（约 8 千）在同一轮里完全相同，可以被前缀缓存复用。以上用时是同一台 Spark 上还有别的整理器和评测在跑时测的。

同一设计两次运行之间 B³ F1 就能差 0.01–0.02，一次错误的大合并就能让难干扰泄漏翻倍，所以设计是按两个 dev 场景一起、
优先看有没有灾难性的大合并来定的：第 1–2 轮 guided decoding 会把模型想说的（不允许的）事件编号改成一个允许的编号；
第 4–8 轮模型把一个大项目的工单、接口、演示并进项目本身（"是它的前置步骤"）。

### 技能用例（`evals/evals.json`，12 个虚构用例 × 3 次）

`eval/run_skill_evals.py --skills event-consolidate --n 3`：最终版本的 SKILL.md **36/36 次通过**（12 个用例 3 次全过）。
中间版本是 35/36：唯一失败的一次是 cons-003（婆婆托用户请店里的师傅去修水管），没有并进店面翻新（这是用例要测的），
但被判成"不是事"而不是"保留"；最终版本写明了"亲友托用户办的事也算事"。

### 已知问题

- 相像的两件事（同一个机器人的实验和开放日演示、同一次求职里的两个 offer）仍会被合并，尤其是一件事的标题里带着另一件事的名字时。
- 一部分噪声小事件被当成碎片并进了真事（"混进真事"上升）；留出的 startup 上事件数没有降到 3 倍以内。
- 小集上整理能把难干扰合成一件；小集的碎片本来就少，整理带来的好处有限。
