# 三个规模场景：lab / startup / pm（全部是合成数据）

每个场景都是 Mac 端 harness 一次性（pace 0）粘贴 1,500–1,600 条素材，由一台 DGX Spark 上的整理器处理完，然后用同一套口径给最终 `/v1/state` 打分。场景定义、生成器和运行记录（`eval/scenarios/scale-*`、`eval/gen/startup`、`eval/tools/scale_lab`）含大量合成素材，没有放进公开快照；本文件是它们的汇总。

- **评分器**：`eval/score.py`（b1419a9）加截图、段真值补丁，指标公式没有改。
- **ID 对齐**：用发送台账把 Mac 端 ID 映射回场景 item_id。
- **基线**：同一场景跑无模型的字符二元组 hash 基线，取三个阈值里最好的一个。
- **限制**：三个场景都只有最终状态可以打分；首轮整理器用墙上时钟。每个场景只跑了一次（n = 1）。
- 本文件是整理者从运行报告里抄出的汇总；原始状态文件和截图含大量合成素材，没有入库。

## 诊断

1. **归组远好于无模型基线**：B³ F1 是基线的 2.0–3.6 倍，Link F1 是 3.0–5.0 倍；易混事件泄漏 startup 从 0.83 降到 0.07，pm 从 0.92 降到 0.14。
2. **最大的问题是碎片化**：预测的事件数是真值的 11–17 倍，只有 1 条的事件有 109–233 件；真事常常只被映射到一个小碎片。
3. **人物是第二弱项**：人物关联只有 0.23–0.26；同名加英文后缀的记录没有合并；代码和表格里的词（`ValueError`、`p-value`、「抄送」）被当成了人；同名异人的地方没有提问。
4. **状态卡基本可信**：计划写成已完成按护栏计 0、按真值计最多 1；查不到来源的日期 0–2；卡片事实召回 0.49–0.65。
5. **速度约 4 条/分钟**：1,600 条要 6.3–7.2 h。event-brief 有 49–64% 的调用被校验拒掉，却吃掉约 60% 的输入 token，是最大的可省之处；event-assign 串行执行，任务并发恒为 1。
6. **界面问题**：一件事里的人一多（约 15 个以上），人物行横向溢出把事件页推出画面；已在 Mac 端修复为「放得下的完整人名 + N」。

## lab 合并前后（离线合并实验，未进入默认流程）
