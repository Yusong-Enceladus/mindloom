# 候选检索召回率（recall@k）

整理器给每条新素材归事件分两步：先用 `skills/event-assign/scripts/candidates.py` 从所有活着的事件里挑出前 k 个候选（现用 k = 5），再让 event-assign 在这 5 个里判断。**真事件不在前 5，模型就不可能把素材归对**，所以 recall@5 是归事件准确率的上限。这里单独测这一步，比较检索用的文本向量：Qwen3-Embedding-4B、现用的 Qwen3-Embedding-0.6B、词法基线（字二元组哈希，就是评测里"词法"基线用的 `HashEmbedClient`），以及不用向量的退化模式。

全部是合成数据；holdout-week-v2 的金标准只读，没有据此改任何参数或提示词。

## 结果

候选分数 = 0.55 × 余弦相似度 + 0.20 × 时间接近 + 0.15 × 共同人物 + 0.10 × 同一来源（与线上一致）。"只看相似度"列只按向量余弦排序，用来看向量本身的区分力。

**dev-week-v1**：计分 69 条（共 82 条；9 条是事件的第一条、4 条噪声，候选池里没有真事件，不计分），候选池平均 7.75 个事件

### 时延和内存

在 Spark 本机回环上测，文本就是整理器要嵌入的内容（来源 App 名 + 素材正文，截至 2000 字；两场景共 121 条非截图素材，中位 47 字、最长 379 字），单条请求顺序发、每条 3 遍（`bench_embed.py`）。node-a 是整理器所在的 Spark（现用 0.6B 端点 :8013，与 Qwen3.6 主模型同卡）；node-b 是为 4B 临时起服务的另一台 Spark（跑到一半另一个工作流在同卡上起了 VLM 评测）。两台都是 GB10、vLLM 0.30.0、`--runner pooling --max-model-len 8192 --max-num-seqs 16 --enforce-eager`。

| 端点 | 维度 | 单条 p50 / p95 ms | 16 条一批 条/秒 | 进程 GPU 内存 | 权重 | 同卡负载（测完采样的 GPU 占用） |
|---|---:|---:|---:|---:|---:|---|
| Qwen3-Embedding-4B，node-b，vLLM util 0.16 | 2560 | 43.35 / 50.81 | 125.4 | 18.7 GiB | 7.56 GiB | 另一 VLM 评测，39% |
| Qwen3-Embedding-4B，node-b，重测 | 2560 | 43.15 / 48.09 | 121.8 | 18.7 GiB | 7.56 GiB | 另一 VLM 评测，95% |
| Qwen3-Embedding-0.6B，node-b，vLLM util 0.05 | 1024 | 13.64 / 15.88 | 490.3 | 6.0 GiB | 1.12 GiB | 另一 VLM 评测，39% |
| Qwen3-Embedding-0.6B，node-b，重测 | 1024 | 27.46 / 33.74 | 214.7 | 6.0 GiB | 1.12 GiB | 另一 VLM 评测，95% |
| Qwen3-Embedding-0.6B，node-a :8013（现用） | 1024 | 25.06 / 36.39 | 224.3 | 5.9 GiB | 1.12 GiB | Qwen3.6 主模型，88% |
| 字二元组哈希，进程内 | 256 | 0.03 / 0.11 | 21182.4 | 0.0 GiB | 0 | — |

进程 GPU 内存是 vLLM 按 `--gpu-memory-utilization` 预留的量（权重 + KV 缓存，Spark 是统一内存，占的就是主机内存），不是权重本身。4B 在 util 0.12 时有一次启动报告 KV 缓存只剩 0.81 GiB、放不下一条 8192 token 的请求（统一内存上 vLLM 的可用内存估算受同机其他进程影响），所以用了 0.16；整理器每条最多 2000 字，把 `--max-model-len` 降到 2048 可以更省。向量按 JSON 存在 SQLite 里，4B 每条约是 0.6B 的 2.5 倍。回放里整理器自己的嵌入调用（每条素材一次）p50：0.6B 在 node-a 为 31–37 ms，4B 在 node-b 为 43–45 ms（holdout 和 dev 重跑那两次 87–97 ms，与同卡 VLM 评测重叠）。

## 结论

- **向量是检索的主力**。去掉向量（整理器在嵌入服务挂掉时的退化模式），dev 的 R@5 从 98.6% 掉到 78.3%，压力池从 98.1% 掉到 59.6%，接近随机（45.2%）。
- **词法基线不够用**。池子一大，字二元组哈希的 R@5 只有 76.0%（压力池漏掉 25 条），0.6B 是 98.1%；只看相似度的 R@1 差距更大（51.9% 对 89.4%）。
- **4B 比 0.6B 只好一点**：R@5 在三个集合上 100 / 100 / 99.0 对 98.6 / 100 / 98.1（dev 少漏 d7-04，压力池少漏 d5-08）；只看相似度的 R@1 高 1.5–5.7 个点。代价是单条时延约 1.6–3.2 倍、预留内存约 3 倍、存储 2.5 倍。在现在的 k = 5 下，归事件的上限基本不受 0.6B 限制，继续用 0.6B。
- **漏掉的主要原因不是向量，是时间和来源项**。在所有有向量的条件下，融合分数的 R@1 都比只看相似度低（0.6B：dev 91.3 → 87.0，holdout 91.4 → 77.1）：时间项让"这几天一直在动的大事件"（如 ev_nanan_po2611、ev_sign）压过相似度更高的真事件。0.6B 仅有的两条前 5 漏掉也是这样：d7-04（"磨豆机的钱退回来了，459块"，微信口述）相似度排第 1（0.70，远高于其他），但退货事件最近一条在 2.7 天前、来源只有 Claude 和淘宝，融合后掉到第 8（压力池第 11）；d5-08（在 Claude 里问会员小程序上线清单）相似度排第 2，被最近在动、同样有 Claude 来源的周年市集事件压下去。要不要调低时间/来源权重（或把 k 提到 8）应在 dev 上另做实验再定，这次没有改。
- **截图素材**：截图先由 Qwen3.6-35B-A3B NVFP4 读图（screenshot-read，摘要 + 转写一起嵌入），压力池里 5 条截图全部进前 5，0.6B 的 R@1 为 4/5、4B 为 5/5，词法基线为 2/5。读图只在第一次运行调用模型，之后所有条件用同一份缓存，保证各向量看到的截图文字一样。

## 怎么测的

`run_retrieval.py` 在进程内起真实的整理器（FastAPI 应用，和 `eval/run_eval.py` 一样通过 `POST /v1/items` 送素材），每条素材走线上的全部检索路径：读图、人物、整理器要嵌入的文本、`event_features()`、`candidates.py`。只替换"放到哪个事件"这一步：用金标准放（归到它已存在的第一个金标准事件；金标准事件的第一条新建事件；无标签的噪声留在未归档），所以每一步的候选池（事件集合、中心向量、时间跨度、人物、来源）都是"归事件全对"时会有的样子。

- 计分对象：候选池里已有真事件的素材。多标签素材只要任一已存在的金标准事件进前 k 就算命中。
- 回放时让候选数不设上限，记录整条排序；线上 k = 5 就是同一排序的前 5（`rank_candidates` 先排序后截断）。
- 不跑 event-brief 和 home-rank（检索不读标题和状态行）。唯一受影响的是 event-brief 标记的"偏离锚点"素材不参与匹配，这里没有这种标记。
- 每条素材只计第一次检索；未归档素材之后的重查不计。
- 同一端点重复运行结果完全相同（`dev-q06-rep`、`dev-q4b-rep`，分数最大差 0.0005）；0.6B 换一台机器跑（`node-b/dev-q06`），dev 融合 R@1 从 87.0 变成 88.4（1 条近乎平分的排序翻转），这是数值误差的量级。
- 随机排序行是解析期望：池子 n 个事件、其中 g 个是真事件时，前 k 命中的概率 1 − C(n−g, k)/C(n, k)。

## 文件

- `run_retrieval.py`：回放和计分。`--embedder url|hash|none`，输出 `items.jsonl`（每条素材：金标准、候选池、完整排序和分项分数，不含正文）和 `summary.json`。
- `bench_embed.py`：端点时延、吞吐、进程 GPU 内存。
- `merge_scenarios.py`：生成压力池场景。
- `report.py`：由 `results/` 生成上面的表。
- `results/node-a/`、`results/node-b/`：本次所有运行；`node-b/serve_log_excerpt.txt` 是两个嵌入服务的启动参数和 vLLM 报告的权重/KV 缓存大小。

复现（在 Spark 上，仓库根目录）：

```bash
python3 eval/retrieval/run_retrieval.py --scenario eval/scenarios/dev-week-v1/scenario.json \
  --embedder url --embed-url http://127.0.0.1:8013/v1 --vision-url http://127.0.0.1:8000/v1 \
  --reading-cache /tmp/readings/dev-week-v1 --out /tmp/retr-dev-q06
python3 eval/retrieval/run_retrieval.py --scenario eval/scenarios/dev-week-v1/scenario.json \
  --embedder hash --reading-cache /tmp/readings/dev-week-v1 --out /tmp/retr-dev-hash
python3 eval/retrieval/bench_embed.py eval/scenarios/dev-week-v1/scenario.json \
  eval/scenarios/holdout-week-v2/scenario.json --embed-url http://127.0.0.1:8013/v1 --out /tmp/bench-q06.json
python3 eval/retrieval/report.py
```

4B 从 ModelScope `Qwen/Qwen3-Embedding-4B`（master，逐文件 sha256 校验）下载，用 `vllm serve <dir> --runner pooling --gpu-memory-utilization 0.16 --max-model-len 8192 --max-num-seqs 16 --enforce-eager` 起服务；没有读图模型的机器用 `--vision-model <id>` 重放读图缓存。
