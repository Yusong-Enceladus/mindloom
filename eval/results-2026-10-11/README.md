# 决赛实测（2026-10-11）：Skill 路由对自由 Agent，以及 DGX Spark 上的部署选择

决赛前在 DGX Spark（GB10，121 GiB 统一内存）上做的六组测量。全部是合成数据：两个合成小场景（dev-week-v1 82 条、holdout-week-v2 46 条）、规模场景 lab 的素材、32 条冻结的 Skill 请求（由合成素材生成，平均输入 22,438 token）、14 张合成聊天截图。这里只有计数、分数和配置；原始运行记录（请求、输出、功率采样、机器日志）留在私有仓库，没有入库。

口径：

- **功率**一律是 **GPU 报告功率（nvidia-smi）**：`nvidia-smi --query-gpu=power.draw -lms 500` 采样，在请求窗口内按时间积分；在 GB10 上它不含 CPU、内存和整机其余部分，不是插座功率。
- **NVFP4 在 GB10 上不是原生 FP4 计算**：vLLM 0.30.0 的启动日志写的是 `MarlinNvFp4LinearKernel` 和 `MARLIN` NvFp4 MoE 后端，也就是 Marlin W4A16（FP4 权重、BF16 激活）。原生 FP4 后端没有测。
- 默认服务配置：Qwen3.6-35B-A3B NVFP4，vLLM 0.30.0，fp8 KV，FlashInfer 注意力，`--max-num-seqs 8`，MTP 投机 3 token。
- 每组的重复次数写在各自一节里，都很少；没有置信区间。

## 1. 固定 Skill 路由 vs 自由 Agent 循环

A = 现在的整理器（固定路由 `JOB_TO_SKILL`、SKILL.md、引导式 JSON、确定性校验和重试、拆段、写卡片、排首页）。B = 同一个模型（Qwen3.6-35B-A3B NVFP4，temperature 0，关闭思考）在一个四工具循环里自己决定：`search_events`、`attach`、`new_event`、`ask_user`，系统提示只有一句「把每条素材归进已有的事或者新建一件事，拿不准就问」，每条最多 8 次工具调用。候选检索和 A 用同一份代码和同一个向量模型。评分器是未修改的 `eval/score.py`。每组每集 2 次，从空库开始，串行，推理并发 1。

| 组 / 数据集 | B³ F1 r1 / r2（均值） | 每条 p50 / p95 秒 | 输入 / 输出 token（每次运行均值） | 模型请求 |
|---|---|---|---|---|
| A / holdout-week-v2 | 0.817 / 0.823（**0.820**） | 11.72 / 52.95 | 1,007,382 / 53,270 | 202 |
| B / holdout-week-v2 | 0.619 / 0.687（**0.653**） | 1.69 / 3.14 | 161,954 / 5,036 | 98 |
| A / dev-week-v1 | 0.796 / 0.778（**0.787**） | 9.24 / 39.62 | 1,349,832 / 64,604 | 273 |
| B / dev-week-v1 | 0.682 / 0.611（**0.646**） | 2.06 / 4.48 | 295,650 / 8,586 | 166 |

- A 比 B 高 0.167（留出）和 0.141（dev）；A 用的 token（输入加输出）是 B 的 6.35 倍（留出）和 4.65 倍（dev），即约 4.6–6.4 倍。
- 两组都没有 schema 违规，也没有写进库的非法引用。
- 这是**完整的 Skill 系统对一个最小四工具 Agent**，不是只改路由这一项：B 没有拆段、卡片、排序、合并和人物环节，也没有校验和重试。A 的 token 里包括这些环节。只有两个合成场景、128 条素材、每组 2 次。

## 3. NVFP4 vs FP8 vs BF16（Qwen3.6-35B-A3B）

质量用 `eval/run_eval.py --condition skills`，dev-week-v1 和 holdout-week-v2 各 2 次；吞吐用 32 条冻结请求，8 路并发。三种格式都开 MTP 3。NVFP4 和 FP8/BF16 在两台同配置的 Spark 上测。

| 格式 | B³ F1（4 次均值） | c8 输出 tok/s | c8 条/分 | GPU 报告功率（nvidia-smi）W | tok/J | 权重 GiB |
|---|---|---|---|---|---|---|
| NVFP4（Marlin W4A16） | 0.8360 | 231.9 | 6.42 | 61.5 | 3.77 | 20.23 |
| FP8 | 0.8177 | 141.8 | 4.07 | 49.4 | 2.87 | 34.32 |
| BF16 | 0.8105 | 123.3 | 3.68 | 46.2 | 2.67 | 65.39 |

- B³ F1 在噪声以内：同一格式两次 dev 之间能差 0.08，三种格式各自的单次结果都落在 0.78–0.86。能说的是 NVFP4 没有看到准确率下降。
- NVFP4 的吞吐是 FP8 的 1.6 倍、BF16 的 1.9 倍；同样的内存预算下 KV 池多约 55%（40.10 对 25.84 GiB）。
- FP8 的 MoE 走了 DeepGEMM，vLLM 对这个组合在本架构上有警告；FP8 吞吐偏低是否与此有关没有单独验证。

## 4. 一台 Spark，多人共用

一份整理服务，每人一个独立空间和 SQLCipher 库，每个空间一个整理 worker（`ORGANIZER_WORKERS=1`，和演示实例相同）；Qwen3.6、Qwen3-Embedding-0.6B、Step3-VL-10B 和整理服务同驻一台 Spark。每人 100 条不同的 lab 文字素材，180 秒内注入。每轮 1 次。

| 用户数 | 完成素材/分 | 首次出卡 / 入库 | 首次出卡 p50 / p95 秒 | Jain 公平指数 | 逐人 p95 最大/最小 |
|---|---|---|---|---|---|
| 1 | 4.43 | 95/100 | 475.6 / 1072.3 | 1.000 | 1.00 |
| 2 | 5.97 | 185/200 | 720.4 / 1589.0 | 0.999 | 1.14 |
| 4 | 6.40 | 385/400 | 1406.9 / 3162.7 | 0.994 | 1.34 |
| 8 | 7.87 | 753/800 | 2525.5 / 5282.5 | 0.996 | 1.28 |

- **突发**：8 人照常，user 1 在第 90 秒另导入 300 条。其他 7 人的首次出卡 p95 是 5268.4 秒，没有突发时 5275.6 秒（1.00 倍）；突发只堆在导入者自己的队列里（7200 秒上限内这 300 条出卡 66 条，没有排空）。
- **质量**：每人子集上的平均 B³ F1，1 / 2 / 4 / 8 人为 0.799 / 0.751 / 0.714 / 0.697（各人子集难度不同，不是严格的不退化试验）。
- **内存预算**（MemTotal 121.69 GiB，四个服务同驻时已用 103.5 GiB）：

| 项目 | GiB |
|---|---|
| Qwen3.6-35B-A3B NVFP4（vLLM） | 70.72 |
| Qwen3-Embedding-0.6B | 8.60 |
| Step3-VL-10B Q8_0（llama.cpp） | 17.91 |
| 整理服务 | 0.07 |
| 系统和其余 | 6.20 |
| 剩余 | 18.19 |

- 每个空间串行一路，所以 vLLM 同时运行的请求峰值等于用户数，8 路批处理在 1–4 人时用不满；多 worker 的配置没有测。

## 5. NVIDIA Nemotron-3-Nano-30B-A3B NVFP4 vs Qwen3.6-35B-A3B NVFP4

同一套 Skills 和评测（每个场景 2 次），读图结果两边共用同一份缓存，向量都用 Qwen3-Embedding-0.6B。

| 模型 | dev B³ F1 r1 / r2 | holdout B³ F1 r1 / r2 |
|---|---|---|
| Nemotron-3-Nano NVFP4 | 0.471 / 0.559 | 0.609 / 0.610 |
| Qwen3.6 NVFP4 | 0.779 / 0.789 | 0.784 / 0.808 |

- Nano 所有调用都返回了合法 JSON，但更爱提问和新建事件，事件切得很碎；长输出的 Skill（线索图、排序）常被校验器拒掉。
- 输出预算封顶 900 token 的负载探针：Nano 吞吐约为 Qwen 的 45%（c1）和 60%（c4）；Nano 的首 token 更快（p50 0.27 秒对 0.76 秒）。
- 混杂因素：Qwen 开着 MTP，Nano 没有投机解码；提示词是为 Qwen 调的。

## 6. StepFun Step3-VL-10B 读聊天截图：引擎、量化和思考模式

| 引擎 / 量化 | 思考 | 并发 | 发送者 | 时间 | 原文 | p50 秒 | 张/分钟 | GPU 报告功率（nvidia-smi）W | 张/kJ |

| SGLang FP8 | 关 | 4 | 100% | 97.4% | 89.7% | 12.08 | 17.18 | 38.2 | 7.47 |
| llama.cpp Q8_0 | 开 | 4 | 100% | 62.8% | 93.6% | 221.99 | 0.93 | 47.3 | 0.328 |
| SGLang FP8 | 开 | 4 | 100% | 60.3% | 92.3% | 144.40 | 1.17 | 38.0 | 0.513 |
| llama.cpp Q8_0 | 关 | 1 | 100% | 96.2% | 92.3% | 10.35 | 5.61 | 51.6 | 1.81 |
| SGLang FP8 | 关 | 1 | 100% | 96.2% | 89.7% | 12.89 | 4.69 | 43.7 | 1.79 |

- 关思考、4 路并发：SGLang 上的官方 FP8 每分钟读的图约是 llama.cpp Q8_0 的 2 倍（17.18 对 8.56），每 kJ 约 2.9 倍；原文准确率低 2.6 个百分点（70/78 对 72/78）。llama.cpp 这里只有 2 个 slot，比较的是两套部署，不只是量化。
- 开思考在两个引擎上都让时间字段准确率掉到 60–72%，延迟高 10 倍以上：这个任务应当关思考。
- SGLang 0.5.21 在 GB10（SM121）上要补 Python 头文件和 ninja 的 PATH 才能启动。
- StepFun 文本模型 Step-3.7-Flash 没有测：NVFP4 权重 120.4 GiB，一台 121 GiB 的 Spark 放不下。
