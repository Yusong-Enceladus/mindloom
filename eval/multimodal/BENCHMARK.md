# 读图模型 benchmark（mm-v1 test，2026-09-29）

四个能在 Spark 上本地跑的开源视觉语言模型，读同一批 98 张合成图（7 类各 14 张，`manifest.json` 的 test 划分），同一个中性提示、temperature 0、不思考、按 JSON schema 引导解码。每个模型跑两次完整的单路，外加一次并发 4 的吞吐测试。全部是合成数据，没有用户数据离开 Mac。

> 整理器里实际的读图路径（image-read：先判类型、再按类型抽取、校验和重试）在同一个 test 上的数字见 `skills/image-read/BENCHMARK.md`。

## 结论

**七类都推荐 Qwen3.6-35B-A3B NVFP4（vLLM）**（比赛演示实例另有一个可关掉的读图路由，把聊天截图交给 Step3-VL，见下面"读图路由"一节）：质量在每一类都是最好或并列最好，单路 p50 2.6 s，并发 4 时每分钟 34 张。代价是内存：vLLM 按 `gpu-memory-utilization 0.45` 预留了约 50 GiB（其中 KV 缓存约 24.5 GiB）。

- **Qwen3.6 Q8_0（llama.cpp）** 是同一个模型，准确率和 NVFP4 差不多（差别只有一两个字段，属于噪声），但单路慢一倍，并发吞吐只有它的三分之一（这个实例只开了 2 个槽位）。没有 vLLM 时可以用它。
- **Qwen3-VL-8B-Instruct Q8_0** 内存最小（19 GiB），图表数值、幻灯片、扫描件和大模型一样准。但它会给聊天里没画时间标签的消息补上时间（时间准确率 85.9%），小票上错了一个日期和一个明细。它是稠密 8B，单路反而比 3B 激活的 Qwen3.6 慢。
- **Step3-VL-10B Q8_0** 不建议用来读图表（数据点 89.7%、趋势 40%）和聊天（文件气泡拆成两条，条数一致只有 85.7%），而且四个里最慢（单路 p50 12.6 s）。

## 读图路由：聊天截图改由 Step3-VL 读，其余仍是 Qwen3.6 NVFP4（2026-10-07）

上面的四模型对比里，Step3-VL-10B 在聊天发送者上 100%，读图表和速度上不如 Qwen。所以整理器现在有一个读图路由（`spark/organizer/image_router.py`，`ORGANIZER_IMAGE_ROUTER=stepfun-chat`）：image-read 的类型步（一个 64 token 的短请求，仍由 Qwen3.6 NVFP4 做）判出 `chat_screenshot` 时，抽取这一步改由 Step3-VL-10B（llama.cpp 原生接口，预填空思考块）读；图表、幻灯片、手写、小票、扫描件、标签和 other 都不动。Step3-VL 不可达、拒绝请求，或它的抽取两次都过不了校验器时，由 Qwen3.6 重读，所以读图不依赖 Step3 服务在不在。路由计数（每个类型由哪个模型读了几张，只有计数）写进日志，也在 `/v1/infra/health` 的 `organizer.image_reads` 里。

下面全部是合成数据。节点是同一台装着 vLLM Qwen3.6 NVFP4（`:8000`）和 llama.cpp Step3-VL-10B Q8_0 + mmproj F16（`-np 2`，ctx 32768，GPU 16.8 GiB）的 Spark；`results/load/router-spark-demo-part1.tsv` 每 5 秒记录两个服务的在跑/排队数，整个第一部分没有别的客户端（在跑数不超过 1，没有排队）。复现脚本是 `eval/multimodal/imgread/run_router_bench.sh`，表格由 `router_report.py`、`e2e_compare.py`、`shots_placement.py` 从 `eval/multimodal/imgread/results/` 里已保存的输出算出，不再调用模型。

怎么读这两张表：

### 二、整个整理器，三个合成场景（全部 Qwen 对路由）

整个整理器（`eval/run_eval.py`，有技能，replay 时钟，Qwen3.6 + Qwen3-Embedding-0.6B）跑 dev-week-v1（82 条，3 张聊天截图）、holdout-week-v1（32 条，1 张）、holdout-week-v2（46 条，4 张）。先跑全部 Qwen 并录下每个模型请求，再用同一个回放缓存跑路由；请求完全一致才回放（命中 42 / 21 / 18 次，其余都重新问了模型，因为只要上游一条输出不同，后面的请求就不一样），所以**两次运行实际上是各自独立的**。dev 另外各重复了一次（没有缓存，两个条件并行跑，墙钟不可比）。

| 场景 | 条件 | 读图的模型 | B³ F1 | B³ P | B³ R | 链接 F1 | 进展行事实召回 | 困难干扰泄漏 ↓ | 预测 / 金标准事件数 |

| dev-week-v1 | 全部 Qwen · r1 / r2 | Qwen 3 张 | 0.822 / 0.795 | 0.976 / 0.931 | 0.710 / 0.693 | 0.855 / 0.824 | 0.346 / 0.404 | 0.000 / 0.000 | 11 / 9，9 / 9 |
| dev-week-v1 | 路由 · r1 / r2 | Step3-VL 3 张 | 0.767 / 0.802 | 0.892 / 0.923 | 0.673 / 0.709 | 0.733 / 0.837 | 0.423 / 0.308 | 0.179 / 0.357 | 10 / 9，10 / 9 |

- **8 张截图都归进了正确的事**（`shots_placement.py`：看截图所在事件里其他素材的金标准事，多数是它自己的事），全部 Qwen 和路由一样，dev 的两次重复也一样。
- **整体指标没有显示路由更好**。holdout 两个场景和全部 Qwen 在同一水平（单次运行）；dev 的 B³ F1 均值 0.785 对 0.809，困难干扰泄漏在路由的两次运行里都不为 0（0.179、0.357），全部 Qwen 的两次是 0。过去这份 dev 上有技能的 Qwen 运行（不同代码版本，15 次，不含按金标准归事件的 oracle）：B³ F1 0.685–0.809，困难干扰泄漏多数是 0–0.143，最早的两次是 0.714。路由两次的 B³ F1 在这个范围内，泄漏 0.179、0.357 高于其中多数运行的上沿，n = 2，不能下结论。
- 能查到的线索都指向截图之外：被泄漏的干扰素材 d1-15 的归属发生在任何一张截图之前（时间更早），两次路由运行里它的第一次判断（`new` 和 `attach`）本来就和全部 Qwen 的两次（都是 `ask`）不同。路由两次运行比全部 Qwen r1 多出的未归入素材是 d7-08（一条要求总结三件事的口述），但全部 Qwen r2 里它同样未归入，所以那不是路由的特征。没有做过能把"读图改变"和"Qwen 本身不稳定"分开的配对实验，所以这里只记录，不归因。
- 读图本身的差别可以看到：Step3-VL 写的一句话摘要常以群名开头（"栗壳翻新群内，…"），Qwen 的不带群名；Step3 有一处用词出错（dev 里一张群通知的摘要写成"两周周年市集"）。摘要只用来给整理器提示，原话仍来自逐字转写。

### 三、故障回退（实测）

把路由指向一个没有服务的回环端口，在 dev 的 2 张聊天截图上跑真实的 image-read 路径：两张都由 Qwen3.6 读完（`ok`，3.7–4.0 s），计数里记下 2 次 `unavailable` 回退，没有异常。回退只改变"谁读"，不改变校验器和重试。单元测试（`spark/tests/test_image_router.py`，12 个）另外覆盖：服务拒绝请求、抽取过不了校验器时由 Qwen 重读、预设只路由聊天、显式路由优先于预设且只允许回环地址、计数线程安全、计数和日志不含内容。

### 结论

在这套合成数据上，Step3-VL 作聊天截图读图器的收益是**发送者全对**（相近名字不再读错）和一个确实在 Spark 上跑的 StepFun 模型；代价是聊天读图慢约 5.7 倍、时间标签和原文逐字一致率更低、多占 16.8 GiB 统一内存。整个整理器的结果没有因此变好，dev 上有一个未查清的负面信号。所以这是一个可以随时关掉的选择（把 `ORGANIZER_IMAGE_ROUTER` 置空即回到全部 Qwen），不是质量上的升级；其余六类图和 other 不使用 Step3-VL。

这组合成图对两个 Qwen3.6 已经接近满分。它们之间的质量差别只有个别字段（例如 NVFP4 在聊天近似名上错 2 条，Q8 在手写上读错了两处数字），两次运行之间的波动也在这个量级，所以这里的差别不能当作量化方式的优劣。拉开差距的是速度。

"编造数字"和"有编造的图"里的实例，逐条看过之后都是**把手写或门牌上的数字读错**（21→27、142→148、155→755、48→84），没有凭空写出图里没有的内容。"无出处字段"只有 Step3 出过一次：它在一张英文价签上加了一个图里没有的"条形码"字段（值为空）。

## 测法

- **数据**：`eval/multimodal` 的 mm-v1 合成集（见 `README.md`）。只报 test 98 张。提示词只在 dev 上写和冒烟：冒烟用的 7 张 dev 图是 board-05、chart-16、chat-06、label-04、receipt-10、scan-13、slide-04；NVFP4 独占副本的预热另用了 7 张 dev 图（chat-06、chart-03、slide-04、board-03、receipt-00、scan-01、label-04），预热结果不计分。
- **提示**：`bench/prompts.py`（`mm-prompt-v1`）。每类一个中性提示和一个 JSON schema，四个模型完全相同。类型是直接给定的，所以这里测的是读，不测分类。看过 test 结果以后，提示词和服务参数都没有改过。
- **请求**：`bench/run_vlm.py` 在 Spark 上通过回环地址调用服务，所以测到的延迟不含 SSH 隧道。每个请求一张图（data URI），temperature 0，`max_tokens` 4096，关闭思考，用 `response_format` 的 JSON schema 引导解码。Step3 走 llama.cpp 原生 `/completion`：预填一段空的 `<think></think>`，schema 放在 `json_schema` 字段，和整理器的 `Step3LlamaNativeClient` 一样。98×2 次单路请求没有一次被截断，JSON 全部合规。
- **计分**：`bench/score_vlm.py`（只读模型输出，不再调用模型）。`--self-check` 把金标准本身按提示的输出格式喂进去，140/140 张都得满分。
  - CER：按 README 的方式规范化（NFKC、去空白、全半角标点等同、去掉"合成数据"），逐行在输出里找最接近的子串。
  - 关键字段 EM：名称、日期时间、数字三类字段的精确匹配率。
  - 编造数字：输出里有、但这张图的金标准里（`text_lines`、所有金标准值、问答答案）找不到的数字，占输出数字的比例。
  - 无出处字段：结构化字段的值不是金标准文字的子串，并且离任何子串都超过 25% 的编辑距离。
  - 有编造的图：出现过上面两种情况之一的图片占比。
  - QA 可答：金标准的每个问题能不能直接从抽取结果里读出答案。
  - 各类型另有专项指标：聊天的发送者、时间、is_self，图表的逐点数值、KPI、趋势，幻灯片的要点召回和精确，手写的划掉和打勾，小票的明细 F1 和自洽，扫描件的表格单元格，标签的字段值。
- **汇总**：质量取两次单路运行的均值，总表是 7 类的宏平均。单路延迟只用没有其他客户端的运行（见下一节）。并发 4 在固定 28 张子集上跑（每类 4 张），吞吐 = 张数 ÷ 墙钟时间，括号里的"单路"是同一子集在单路运行里的速率。内存取 `nvidia-smi` 报告的进程占用：llama.cpp 的内存随 ctx 和槽位数变化，vLLM 的内存是按比例预留的，不等于实际用量。

## 测量条件

`results/load/<节点>.tsv` 每 5 秒记录一次各服务的在跑/排队请求数。报告据此逐次算出"别的客户端在跑"的采样占比：

- **Qwen3.6 NVFP4**：两次质量运行在 spark-F :8000 上，它同时在给另一个代理的评测服务，整个运行期间都有约 3 个别人的请求在跑、7–12 个在排队。所以这两次只用来算质量，它们的延迟（p50 约 10 s）不用。
  延迟和吞吐改在 **spark-C 上一个同配置的独占副本**（:30102）测。权重和 spark-B 逐文件 sha256 一致，与 spark-F 是同一份（`Qwen3.6-35B-A3B-NVFP4` 三个 safetensors）。vLLM 0.30.0 venv 和 FlashInfer/Triton/vLLM 编译缓存经内部链路从 spark-B 整份拷贝。启动参数与 spark-F 上 `ps` 看到的完全相同，只有模型路径和端口不同。两台都是 DGX Spark（GB10，121 GiB 统一内存）。
  同配置的证据：独占副本两次运行的质量（CER 0.3/0.2%，关键字段 EM 98.4/98.2%）与 spark-F 相同。spark-F r1 和 spark-C r1 的输出逐字一致率是 72.4%，和同一台机器上两次运行之间的 68.4% 一个水平。也就是说，vLLM 在 temperature 0 下本来就不完全确定，换节点没有带来额外差异。
  测量期间 spark-C 上只有 TTS 服务（:8200）驻留，它最后一次处理请求在测量开始之前。
- **Qwen3.6 Q8**：r1 期间，另一个客户端一直占着这个服务的第二个槽位（p50 12.6 s）。r2 和并发 4 没有别人（p50 5.4 s），所以延迟只取 r2。这个实例是 `-np 2`，并发 4 时有两个请求在排队，吞吐受槽位数限制。
- **Step3-VL-10B**：r1 在 spark-A :30001（`-np 1`）跑，同一块 GPU 上的 Q8 服务在 39% 的时间里被别的客户端使用。r2 和并发 4 在 spark-C 上用同一份 GGUF、同一个 llama.cpp 版本（d834d44）起的 4 槽副本（:30101）跑，没有别的负载，延迟只取 r2。r1 和 r2 的输出 100% 逐字一致。
- **Qwen3-VL-8B-Instruct**：为这次评测临时部署在 spark-C :30100。GGUF 来自 ModelScope 上的 Qwen 官方仓库，sha256 已校验，许可证 Apache-2.0。两次单路都没有别的客户端，延迟两次合并算。r1 开始时同机还驻留着检索评测的两个 embedding 服务（后来停了），r1 和 r2 的 p50 分别是 10.1 s 和 10.0 s，看不出影响。
- 负载日志比最早几次运行晚开了约 11 分钟，覆盖率不足的运行在 `results/tables.md` 的"每次运行"表里标了出来。
- 两次运行输出逐字一致的比例：NVFP4 68.4%（spark-F 两次、spark-C 两次都是这个数）；Q8 82.7%（r1 和别人的请求一起批处理）；Step3 和 Qwen3-VL-8B 都是 100%。

## 已知问题与局限

- **合成数据、样本小**：每类 14 张，难例标签有的只有 1–3 张。合成图比真实截图和照片干净，所以绝对分数偏高，适合用来比较模型，不适合当作真实场景下的准确率。
- **划掉召回**：board-12 上"Lemons"的划线画在了基线附近，看起来更像下划线，四个模型都没把它判成划掉。所以 83.3% 的上限来自这张图的渲染，不全是模型的问题。金标准不在看过 test 之后改，这里只记下来。
- **小票 CER** 主要来自两栏抬头（"Bill to … Invoice no. …"在同一行）被模型拆成两行，以及模型多抄了表头和"PAID"印章。按行找最接近子串的 CER 会因此受罚，但关键字段并没有错。
- **标签字段的严格一致**受字段边界的口径影响，同时报了"包含"口径。
- **看过 test 输出后改过的评分口径**：群聊标题里画出的人数"(N)"、小票时间的 12/24 小时写法和单号前的"#"、付款方式的大小写、标签值的"包含"口径，以及本次新加的一条：聊天文件气泡下画出的文件大小（如"86 KB"，渲染器画了，但金标准只记"[文件 名称]"）不算编造数字。最后这条只影响 Step3，它会把文件大小单独读成一条消息。这些改动都只是让评分和图上实际画出的文字对齐，对所有模型一视同仁，改完后 `--self-check` 仍然全部满分。
- **没测**：模型本身的思考模式、更大的并发、更长的上下文（多图）、真实照片、提示词注入。

## 复现

```bash
# 在 Spark 上（服务只监听 127.0.0.1）；mm/ 下放 manifest.json、images/ 和 bench/{run_vlm.py,prompts.py}
python3 bench/run_vlm.py --root . --split test --backend openai --url http://127.0.0.1:8000  --label qwen36-nvfp4-vllm --out out/qwen36-nvfp4.r1.jsonl
python3 bench/run_vlm.py --root . --split test --backend openai --url http://127.0.0.1:30000 --label qwen36-q8-llamacpp --out out/qwen36-q8.r1.jsonl
python3 bench/run_vlm.py --root . --split test --backend step3  --url http://127.0.0.1:30001 --label step3-vl-10b-q8   --out out/step3.r1.jsonl
SUB=chat-00,chat-01,chat-02,chat-03,chart-00,chart-01,chart-02,chart-04,slide-00,slide-01,slide-02,slide-03,board-00,board-01,board-02,board-04,receipt-01,receipt-02,receipt-03,receipt-04,scan-00,scan-03,scan-04,scan-05,label-00,label-01,label-02,label-03
python3 bench/run_vlm.py --root . --ids $SUB --concurrency 4 --backend openai --url http://127.0.0.1:30000 --label qwen36-q8-llamacpp --out out/qwen36-q8.c4.jsonl

# 在 Mac 上（只读 results/raw，不调用模型）
python3 eval/multimodal/bench/score_vlm.py --gt-root eval/multimodal --self-check
cd eval/multimodal && python3 bench/report.py --root . --models bench/models.json
```

`bench/models.json` 记录每个模型的哪几次运行用于质量、延迟和吞吐，以及每次运行在哪台机器、哪个端口。`run_vlm.py` 可以断点续跑，并在输出旁边写 `.meta.json`，记下开始和结束时的 GPU 进程与内存、服务的在跑/排队数。
